# WD-82 — Conflict handling when importing a browser's own data

**Epic:** EP-11 · **Wave:** 4 · **Priority:** P1

## Overview

As a user importing existing data, I want sensible conflict handling (e.g.
a local watch with the same URL as one already on the server), so import
doesn't create confusing duplicates.

WD-81 built the import and left this ticket one seam: the URL twin in
`watch-sync.js`'s `runSync()`. Most of both criteria already held (watches
matched by URL, listings upserted by WatchDesk on `source_key`). This ticket
found how much, proved it with tests, and built the gap:

1. **"The same URL" was the same string.** A trailing slash, `www.`, the
   order of the parameters, a tracking parameter or a fragment made the same
   search a second watch. It is now the same *search* (`watch-url.js`).
2. **Skipped listings were counted as uploaded.** The end state said
   "41 listings uploaded" when 11 of them were already in the account. Added
   and already-there are now counted and said apart, and by site.
3. **A posting held under two local watches was sent twice**, and its
   applied mark could be lost. It is sent once.
4. **Two watches becoming one dropped what one of them had seen.**

One pull request, this repository only. No web change and no new endpoint.

## Acceptance criteria

- [x] A local watch matching an existing server watch (same site + URL) is
      merged, not duplicated.
      — `runSync()` matches by `watchKey()` (`watch-url.js`): the site and
      the URL but for its spelling. The local watch becomes the account's
      watch, its feed and seen postings are attached to it, and nothing on
      WatchDesk is changed. Tests: `tests/watch-url.test.js` (44),
      `tests/import-conflicts.test.js` ("a second device: the account
      already has some of the watches", and the first-device cases),
      `tests/watch-sync.test.js` ("the same search under another spelling
      (WD-82)"). Real browser: Testing notes.
- [x] A local feed entry matching an existing server listing (same
      source_key) is skipped, not duplicated; everything else is inserted.
      — WatchDesk decides (one row per `(user_id, source_key)`); the import
      sends each posting once, marks "applied" only on rows WatchDesk says it
      inserted, and counts `listingsExisting` apart from `listingsNew`.
      Tests: `tests/import-conflicts.test.js` ("a second device: the account
      already has some of the listings", "an import that is run again").
      **One thing "skipped" does not mean**, because the route cannot be
      asked for it: WatchDesk refreshes the title, URL and Easy Apply flag of
      a posting it already has with the ones sent, as on every later
      sighting (below, and "What the API does not let the import do").

## What counts as the same search

`watchKey(url)` in `watch-url.js`. Two URLs with the same key are one search
on one site. The site is derived from the URL on both sides, by `sites.js`'s
`siteForUrl()`, and is part of the key.

**Folded** (cannot change what a search finds): `http` / `https`; the case
of the host; a leading `www.`; a default port; trailing slashes on the path;
the percent-encoding of the path (an escape of a character that needs none
is decoded, any other is upper-cased); the order and encoding of the query's
parameters; a fragment; parameters that only say where a link was clicked
(`utm_*`, `gclid`, `gbraid`, `wbraid`, `dclid`, `fbclid`, `msclkid`, `yclid`,
`igshid`, `mc_cid`, `mc_eid`, `_ga`, `_gl`; on LinkedIn also `trk`,
`trackingId`, `refId`, `lipi`); and whatever the site's own `normalizeUrl()`
rewrites (LinkedIn: the search-results page shape, `currentJobId`, `origin`,
`referralSearchId`, and `sortBy`, which the extension always sets to `DD`).

**Kept** (so they make two searches): every other parameter and its value,
case included; a parameter that is present but empty; a parameter given
twice; the path and its case; an escaped `/`; any subdomain other than
`www.` (a regional LinkedIn or Glassdoor host); a non-default port. A URL
that is not an http(s) address is the same search only as itself.

**How this sits with WatchDesk.** The server has no such rule and needs
none: it stores a URL as it is sent (trimmed; a LinkedIn search rewritten by
its copy of `normalizeLinkedInUrl`) and allows two watches with the same URL
(WatchDesk WD-52, decisions 1 and 11). So the two sides cannot disagree
about a row: which of the account's rows a local watch *is* is decided here
alone, and the only thing the decision does is choose between "use that row"
and "POST a new one". What the server would treat as two rows and this rule
as one search: the account keeps both rows; a local watch that is that
search becomes one of them (the one spelled like it, else the oldest) and
the other stays as it is. The reverse, a search this rule keeps apart that
is really the same, is a second watch: visible, harmless, deletable. That
asymmetry is why the rule is conservative.

## What "merged" means

| Field | Wins | Why |
|---|---|---|
| Label | The account's | The user already named it there, and other browsers and the web show that name. |
| Paused / running | The account's | The same. A watch paused in the account is paused here after the import; the end state says so when it differs. |
| URL (its spelling) | The account's | The list of a connected browser is the account's (WD-54). |
| Seen postings (`seenIds`) | Both, joined | Neither watch's postings are then announced as new again. |
| Last check, last result, error count | The watch that was already being checked, else the local one's | Display only. |
| Feed entries | Kept; their `watchId` becomes the account's watch | As WD-54. |

Nothing on WatchDesk is written because of a match: no PATCH, no DELETE.

## What the API does not let the import do

For the main session to file against the web repository if wanted. Neither
blocks this ticket.

1. **Leave an existing listing's fields alone.** `POST /api/listings/ingest`
   is "insert or refresh": a posting the account already has gets the
   title, URL and Easy Apply flag that were sent, and a salary or workplace
   type it lacked. An import sends what the browser read some time ago, so a
   title the account has from a newer check can be replaced by an older one
   (until the next check sends the current one again). Status, watch, label,
   posted date and date found are never touched. To make "skipped" mean
   "unchanged", ingest would need an insert-only mode (`ON CONFLICT DO
   NOTHING`) for this caller, or a device-token route that says which
   `sourceKey`s the account has, so the extension could leave them out.
2. **Carry an applied mark onto a listing the account already has as "new"
   or "viewed".** Unchanged from WD-81: the ingest answer names only the
   rows it inserted, so the extension has no id to PATCH. Such a mark is
   counted and said ("applied marks not carried over"). It would be safe to
   carry (a status is never downgraded by it) if the answer named every
   row's id and status.

## Decisions taken

The handoff said to proceed without stopping. Each is the option I would
have recommended and is open to challenge at review.

1. **The match is by search, not by string, and errs towards "different".**
   A second watch can be deleted; two searches merged into one lose one.
2. **`http` and `https` are one search**, and so is a `www.` prefix. Every
   supported site redirects one to the other; no other subdomain is folded.
3. **The rule is the same in every path that adds a browser's watch to an
   account**: WD-54's first sync, WD-111's backup import, WD-81's import and
   its "Not now". One rule in one place; a browser connected without the
   import question (one with no data but a default watch) must not double a
   watch any more than an importing one. It changes nothing for a watch the
   account already knows by id, never merges two watches of the account, and
   does not apply to a watch the user adds by hand while connected
   (`addAccountWatch()`): WatchDesk allows that duplicate and the user asked
   for it.
4. **The account's watch wins on label, paused state and URL, and is never
   written to.** Recommended by the handoff. The surprise it can cause (a
   watch that was running here is paused after the import) is said in the
   end state, and both questions now say before the choice that "the account
   keeps its own, with its name, paused state and status".
5. **Of several matching watches of the account: the same spelling, else the
   oldest.** Deterministic, so a resumed import picks the same one.
6. **Two local watches that are the same search: the first in the list is
   the one uploaded**, with its label and state; the second's are not kept
   (counted in `watchesMatchedDiffer`). Their seen postings are joined.
7. **`seenIds` are joined when two watches become one**, in every sync, not
   only the import. Otherwise the next check announces postings one of them
   had already seen.
8. **A posting under two local watches goes to the one that found it
   first**, with that entry's fields, because that is where WatchDesk files a
   posting two watches find (WD-57, decision 8).
9. **"Skipped" is counted from WatchDesk's answer**, not predicted: only the
   server knows what the account has, and no device-token route lists it.
   So a skipped posting is still *sent* (see "What the API does not let the
   import do", 1).
10. **`listingsUploaded` is kept** (new + existing) so WD-81's readers keep
    working; the popup no longer shows it as "uploaded".
11. **By-site counts are in the record; no screen** (WD-83's).
12. **The set-aside list ("Not now") is still one per exact URL.** Folding
    spellings there would drop a watch from the only place it is kept.
13. **A new module (`watch-url.js`) rather than more of `sites.js`**:
    `sites.js` is outside ESLint, and this rule is the sync's, not a site
    adapter's. It imports `siteForUrl()` so there is one site rule.
14. **No change to `account-settings.js`, `background.js` or
    `manifest.json`.**

## Known limitations

- **A skipped listing's title, URL and Easy Apply flag become the
  browser's** (above). Not avoidable with the existing routes.
- **A batch WatchDesk stored but never answered for** (a worker stopped in
  that one write) is counted as "already in your account" when it is sent
  again, not as "uploaded", and its applied marks are not carried. Nothing
  is doubled; one count is off by the other. Unchanged from WD-81.
- **A watch created just before a worker is stopped** is matched on the next
  try and counted as "already in your account". Unchanged from WD-81.
- **A posting held under two local watches goes with the one that found it
  first**; if WatchDesk deletes that watch mid-import the posting is counted
  `listingsWatchGone` and not offered to the other watch.
- **The tracking-parameter list is a list.** A parameter not on it keeps two
  spellings apart (a second watch), which is the safe side.
- **A comma or other reserved character written as an escape** (`%2C`) is
  not the same as the character: two watches.
- **"Not now" says nothing about a name or paused state that differed**:
  there is no end state to say it in. The list shows the account's.
- **An import in flight across the update to this version** finishes with
  `listingsExisting` counted only for the requests sent after it.
