# WD-42 — Connect Account from the extension popup

**Epic:** EP-02 Extension Device Auth & Sync Protocol · **Feature:** FT-0201 Device Pairing Flow

## Overview

Adds a **Connect Account** button to the popup. One click starts a device
pairing with WatchDesk (WD-41) and opens `/connect-extension?code=…` (WD-43).
The service worker polls in the background until the user approves or denies,
then stores the device token and shows "Connected to WatchDesk" with the
account's email, read from `GET /api/devices/current` (WD-45).

Being connected changes nothing else yet. Watches, checks, notifications,
the feed and settings work exactly as before.

This is the first ticket built in this repository under WatchDesk, so it also
sets the repository up: `CLAUDE.md` / `AGENTS.md`, a dev-only test harness
(Vitest, ESLint), and a GitHub Actions workflow.

## Acceptance criteria

- [x] Clicking Connect Account opens a new tab at /connect-extension?code=...
      and starts polling in the background.
      — `startConnecting()` in `account-connection.js`. The URL carries the
      code only, never the poll secret. Polling runs in the service worker
      every `pollIntervalSeconds` and keeps going with the popup closed.
      Tests: "asks WatchDesk for a code and opens /connect-extension?code=…",
      "starts polling in the background…". Seen in Edge (see Testing notes).
- [x] On approval, the token is written to chrome.storage.local (never
      chrome.storage.sync) and the popup shows a connected state with the
      account's email.
      — `completePairing()` and `refreshAccount()`. Tests: "pending →
      approved…", "never logs the token or the poll secret, and never touches
      chrome.storage.sync". In Edge: token in `local`, sync keys unchanged,
      popup reads "Connected to WatchDesk | <email> · Edge on Windows".
- [x] Closing the tab before approving leaves the extension in a clear 'not
      connected' state.
      — `chrome.tabs.onRemoved` → `stopPairing(…, "tab-closed")`. The popup
      reads "Not connected to WatchDesk — The WatchDesk tab was closed before
      the code was approved." and offers Connect Account again. Tests under
      "closing the tab before approving". Seen in Edge.

## Decisions taken

The handoff said to proceed without stopping, so these were taken on my
own. Each is open to challenge at review.

1. **Origin in one module, `config.js`.** It has `production`
   (`https://watchdesk-rosy.vercel.app`, the default) and `development`
   (`http://localhost:3000`), and you switch by editing `WATCHDESK_ENV`.
   Both origins are in `host_permissions`. `tests/config.test.js` fails if
   an origin appears in any other shipped file, or if the manifest misses
   one. I did not add a runtime override (for example a storage key):
   anything able to redirect the origin could redirect the token.
2. **Pairing state in `chrome.storage.session`, the token in
   `chrome.storage.local`.** Session storage is memory-only (the poll secret
   never touches disk), survives a worker restart, and is closed to content
   scripts by default. A browser restart clears it, which ends a pending
   pairing; the user starts again with one click. Leaving a ten-minute
   secret on disk to survive a restart did not seem worth it.
3. **"Atomically" is token first, pairing cleared second, and the token
   wins.** The two areas cannot be written in one call. If a worker stops
   between the two writes, the next start sees a token plus a leftover
   pairing and discards the pairing. A token that arrives after the pairing
   was cancelled is still stored: the user did approve, and it is the only
   copy.
4. **Closing the tab cancels.** The code stays approvable on the server for
   its remaining minutes, but the AC asks for a clear not-connected state,
   and a pairing that silently continues with no visible tab is not that.
   **Before cancelling, the extension polls once more**, so approving and
   closing the tab at once still connects. **Cancel** in the popup does the
   same. Navigating the tab elsewhere, for example through `/login`, does
   not cancel; only closing it does.
5. **What the popup shows.** *Not connected*: Connect Account, with the
   reason of the last attempt if there was one (tab closed, cancelled,
   denied, expired, revoked, WatchDesk unreachable, rate-limited with the
   wait, error). *Pending*: "Waiting for approval…", the code, the time left,
   and **Show tab** / **Cancel**. *Connected*: the email and device name.
   Pressing Connect Account while pending brings the existing tab forward
   instead of starting a second pairing.
6. **The popup never calls the API and never sees the token.** It sends
   `account-*` messages; the worker answers with a state object that has no
   token and no poll secret.
7. **401 from `/api/devices/current` discards the token** and shows "This
   browser was disconnected…". Any other failure (offline, 5xx) keeps the
   token and the last known email. The check runs when the popup opens.
8. **No Disconnect button.** The ticket does not ask for one, and revoking on
   WatchDesk's profile page has the same effect. Listed as a follow-up.
9. **Tooling: npm, Vitest, jsdom, ESLint**, all dev-only, matching
   WatchDesk's test stack. `npm` rather than `pnpm` keeps `node_modules`
   flat inside a folder Chrome loads unpacked.
10. **ESLint covers the new modules and the tests, not the legacy files.**
    `background.js` and `popup.js` have six pre-existing findings. A config
    hook refuses to relax the rules for them, and changing those files to
    satisfy a linter is not this ticket's job. Every shipped script gets a
    `node --check` syntax pass instead (`scripts/check-syntax.js`).
11. **The manifest version stays `1.1.0`.** Bumping it is a release
    decision.

## API changes

None on the server. The extension calls, as documented in the WatchDesk repo:
`POST /api/auth/device/start`, `GET /api/auth/device/poll?code=…` with
`X-Pairing-Secret` (WD-41), and `GET /api/devices/current` with
`Authorization: Bearer` (WD-45).

## The polling mechanism and its limits

- **Loop.** `runPollLoop()` reads the pairing from session storage, waits
  until `nextPollAt` (never past `expiresAt`), polls, and writes the next
  `nextPollAt`. It stops on `approved`, `denied` or `expired`, or when
  `expiresAt` passes without an answer.
- **Staying alive.** An MV3 worker is stopped after about 30 s with no
  extension events or extension API calls, and its timers die with it. The
  loop never sleeps longer than 20 s between storage reads, and each read is
  an extension API call, so the worker stays up for the whole pairing, even
  through a long `Retry-After`.
- **Surviving a stop anyway.** The pairing is in session storage.
  `registerAccountConnection()` runs at the worker's top level and resumes
  the loop whenever the worker starts for any reason. A
  `watchdesk-pairing` alarm (period 0.5 min, the `chrome.alarms` minimum)
  exists while a pairing is pending, so the worker is woken at least every
  30 s even if nothing else wakes it. The alarm is cleared when the pairing
  ends.
- **Pacing.** Every `pollIntervalSeconds` (default 3). On 429, wait
  `max(Retry-After, interval)`. On a network failure or 5xx, wait 5 s and
  keep going until expiry. On another 4xx (WD-41's 400), stop with an
  error, since asking again cannot help.
- **One loop per worker.** An in-memory promise guards it, and every change
  to the pairing goes through a small queue, so a poll result cannot bring
  back a pairing that a closed tab or Cancel has just removed.
- **Limits:**
  - After a worker stop, the next poll can be up to about 30 s late (the
    alarm period). In Edge the restarted worker collected the token 29 s
    after approval in one run and 3 s in others.
  - A browser restart ends a pending pairing (session storage is cleared).
    If the user approves afterwards, nobody collects the token; the server
    leaves a device row that can be revoked (ADR 0002 §3).
  - `expiresAt` is compared with this computer's clock. If the clock is off
    by more than the code's lifetime, the extension uses its own ten
    minutes; the server's `expired` answer still ends the pairing.
  - Chrome before 120 rounds the 0.5-minute alarm up to 1 minute.

## Known limitations

- `chrome.storage.local` is readable by this extension's own content
  scripts. They do not read it, and the token is never sent to them, but
  Chrome offers no per-key restriction for `local`. The poll secret is in
  `session`, which content scripts cannot read.
- The connected state is checked when the popup opens, not in the
  background. A revoked device keeps its token until then (nothing uses the
  token yet).
- No Disconnect button. **Reset Extension** does not disconnect.
- With the popup open as a real popup, clicking Connect Account closes it,
  because Chrome closes the popup when a tab opens. Reopening it shows the
  pending state.
- `http://localhost:3000/*` is in `host_permissions` of the shipped
  manifest. It is harmless, but should be removed for a Web Store release
  (see CLAUDE.md).
- Lint does not cover `background.js`, `popup.js` and the other legacy
  scripts (decision 10).

## Testing notes

`npm ci && npm run lint && npm test`. 87 tests in 5 files, all with mocked
`chrome.*` and `fetch` (`tests/helpers/`) and fake timers:

- `tests/account-connection.test.js` (34): start, tab URL, polling cadence;
  pending → approved / denied / expired / stop at `expiresAt`; 429 with
  Retry-After; network error; 5xx; 400; worker restart mid-pairing
  (resume at load, resume from the alarm alone, expiry across a restart,
  token-wins after an interrupted write, browser restart clears it); tab
  closed (cancel, approve-then-close, deny-then-close, other tabs ignored,
  start again); Cancel; connected state (email, 401 → not connected,
  offline keeps the token, no second pairing while connected); secrets never
  logged and `sync` never touched.
- `tests/watchdesk-api.test.js` (21): requests sent and every answer read,
  timeout, non-JSON bodies.
- `tests/popup-account.test.js` (22): every card state rendered into the real
  `popup.html` (jsdom); text, never markup; the countdown outside the live
  region; clicks; refresh on open; 1 s re-read while pending.
- `tests/background-wiring.test.js` (5): `background.js` registers the
  listeners and routes `account-*`; the pairing alarm does not trigger a job
  check; unknown messages unchanged.
- `tests/config.test.js` (5): the single-origin rule and the existing
  permissions.

Mutation check: storing the token in `sync`, skipping the last poll on tab
close, removing the resume at startup, and ignoring Retry-After each make at
least one test fail.

**In a real browser.** Microsoft Edge (Chrome is not installed here), with
Playwright loading the unpacked extension, set to `development`, against a
local WatchDesk (`wd-45-devices-list` worktree, local Postgres, migrations
applied). 22 of 22 checks passed:

- Not connected on first open; existing controls render; the settings panel
  opens.
- Connect Account opens the WatchDesk tab with `?code=…`. Signed out, it is
  sent to `/login` with the code carried in `callbackUrl`. No poll secret
  appears in any URL.
- Pending shows the code. Closing the tab gives "Not connected — the
  WatchDesk tab was closed…", with no pairing state and no token left.
- With a signed-up, verified account, Deny on WatchDesk gives "denied".
- Approve, with the popup closed and the service worker stopped through
  DevTools first (its in-memory marker was gone afterwards). A new worker
  instance collected the token, which landed in `local` and not in `sync`,
  and the pairing state was cleared. The popup showed "Connected to
  WatchDesk | <email> · Edge on Windows" and the token was not in its DOM.
- Revoking the device on WatchDesk, then reopening the popup, discarded the
  token: "This browser was disconnected…".
- No page errors in the popup or the app.
- Separately, the repository root itself (production config,
  `node_modules/` present) loads unpacked: the worker starts and the popup
  renders.

**Not verified:** Google Chrome itself; the production origin
(`watchdesk-rosy.vercel.app`) end to end, since no deployed WatchDesk was
used; a real browser restart mid-pairing (covered by unit tests only); the
real toolbar popup (the popup page was opened as a tab so it stayed open
while the approval tab opened).

## Manual verification (Chrome)

1. Load the repository root unpacked (`chrome://extensions` → Developer
   mode → Load unpacked). For a local WatchDesk, set `WATCHDESK_ENV` to
   `"development"` in `config.js` first and reload.
2. Open the popup: "Not connected to WatchDesk" with **Connect Account**.
3. Click it. A tab opens at `<origin>/connect-extension?code=XXXX-XXXX`.
   Sign in if asked. Reopen the popup: "Waiting for approval…" with the same
   code and a countdown.
4. Close the WatchDesk tab without approving. Reopen the popup: "Not
   connected… The WatchDesk tab was closed before the code was approved."
5. Click Connect Account again and approve on the page (the account's email
   must be verified). Within a few seconds the popup shows "Connected to
   WatchDesk" with your email and the device name.
6. In the service worker console (`chrome://extensions` → "service worker"):
   `chrome.storage.sync.get(null)` has no `watchdeskToken`, and
   `chrome.storage.local.get("watchdeskToken")` has one. Do not paste its
   value anywhere.
7. On WatchDesk's profile page, revoke the device. Reopen the popup: "This
   browser was disconnected from your WatchDesk account."
8. Check that watches, Check now, Open all tabs, the settings panel and the
   feed behave as before.
