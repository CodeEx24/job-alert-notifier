# WD-81 — Offer to import a browser's own data on its first pairing

**Epic:** EP-11 · **Wave:** 4 · **Priority:** P1

## Overview

As an existing user, the first time I log in from an already-installed
extension, I want to be offered an import of my current local watches,
feed, and settings into my new account, so I don't lose months of
accumulated history.

Until this ticket a first connection uploaded the browser's watches without
asking (WD-54) and replaced its settings with the account's (WD-79). Now a
pairing that completes puts the browser on hold: nothing is synced with the
account until the user has answered the popup's question.

```
● ada@example.com
  Chrome on my laptop

IMPORT YOUR EXISTING DATA
This browser has 5 watches, 41 listings and your settings of its own.
Import them into your WatchDesk account? It can take a minute.
 • Import uploads them to your account. They stay in this browser too.
 • Not now keeps everything in this browser and starts the account without
   it. The watch list here then shows your account's watches; this browser's
   own are kept, and you can import them later from Settings.
 • Until you choose, nothing is sent to WatchDesk and this browser keeps
   checking its own watches.
[ Import ]  [ Not now ]
```

One pull request, this repository only. It uses the routes WatchDesk already
has (WD-52, WD-56, WD-57, WD-67); no web change is required. **Two things the
existing routes cannot do are listed under "What the API does not let the
import carry over", for the product owner to decide on.**

## Acceptance criteria

- [x] On first successful pairing (US-009) where local data exists, the
      extension offers 'Import your existing data' before syncing anything
      else.
      — `completePairing()` writes `watchdeskImport: { phase: "connecting" }`
      in the same storage call as the token, and while the record is
      `connecting` or `offered` `isAccountActive()` is false: the watch sync,
      the settings sync, listing ingestion and the watcher report all do
      nothing. The popup shows the card under the account card. Tests
      (`local-import`): "offers the import, and syncs nothing before the
      answer" (after a real pairing, with `sync-watches`, `sync-settings`,
      `check-now`, a pause and an alarm tick all asked for: zero requests to
      the watch, ingest, listing-status and settings routes), "stays on hold,
      sending nothing, until WatchDesk has said whose the account is";
      (`popup-local-import`) "asks the question under the account card, and
      nothing has been sent". Real browser: Testing notes.
- [x] Declining import leaves local data untouched and starts the account
      empty.
      — "Not now" sends nothing. The browser's watches are copied to
      `watchdeskWatchesBeforeConnect` before the first sync, which then
      uploads none of them; the feed is not touched; the settings are kept by
      WD-79's snapshot. Tests: "uploads nothing, keeps this browser's data,
      and starts with the account as it is", "a watch whose URL the account
      already has becomes that watch; the others are set aside, never
      uploaded", "the watch is set aside before the list loses it". Real
      browser: Testing notes.
      **"Untouched" has one consequence that needs saying:** once the browser
      works with the account, the popup's watch list is the account's (WD-54),
      so the browser's own watches are no longer *shown*. They are kept, the
      card says so before the user chooses, and Settings offers the import
      again. See decision 4.
- [x] Accepting uploads existing watches, feed entries, and settings in one
      batch.
      — One click, one progress, one outcome; several requests (the handoff's
      reading of "one batch"). Tests: "uploads the watches, then the feed,
      then the applied marks, then the settings, and removes nothing here",
      "sends a large feed in requests of at most 200 listings, one watch
      each, spaced out", and the rest of "Import". Real browser: Testing
      notes.

## What happens, case by case

Every row has a test of that name or meaning in `tests/local-import.test.js`.

| Situation | What happens |
|---|---|
| Data in this browser, user says **Import** | Watches, then feed, then applied marks, then the stored settings are uploaded. Nothing is removed from the browser. The card ends with what was uploaded and what was left out. |
| Data in this browser, user says **Not now** | Nothing is uploaded. The feed is untouched; the watches are set aside in `watchdeskWatchesBeforeConnect`; the settings are kept in `watchdeskSettingsBeforeConnect` (WD-79). The browser then shows and checks the account's watches and settings, as the server has them. Settings → "Import this browser's data into your account…" asks again. |
| Data in this browser, popup closed / no answer yet | Nothing is uploaded and nothing is lost. **The watcher keeps working on the browser's own watch list and settings, exactly as with no account connected** (add, pause, Reset and a backup import included). The card is there again every time the popup opens. |
| No data in this browser | No offer. The connection behaves as before WD-81: the default watch such a browser shows is uploaded by the first sync (WD-54, decision 2). |
| The account already has data (a second device) | The offer still appears. The only conflict rule is WD-54's: a watch whose URL the account already has becomes that watch (the account's label and paused state win) and is not doubled; a posting the account already has is not doubled (`source_key`) and keeps its status. WD-82 refines this. |
| The same account pairs again (after a disconnect) | Not asked again. If it said yes: as before WD-81. If it said no: still nothing is uploaded, and Settings still offers the import. If an import was cut off by the disconnect: it carries on from where it stopped. |
| A different account pairs | Asked afresh, about what the browser holds then (the last account's list and settings, and the feed). Nothing is sent to it before its own answer. An import that was under way for the first account is dropped. |
| A browser connected before this version | No record, so no offer: it already uploaded its watches under WD-54. |
| WatchDesk has not yet said whose the token is | On hold (`{ phase: "checking" }`, nothing shown, nothing sent) until `/api/devices/current` has answered: whose account it is decides whether to ask. |

"Data in this browser" means a stored watch list, at least one feed entry, or
at least one of the four synced settings stored. A browser that has stored
none of them is showing the default watch and nothing else.

"First" is tracked **per account, by its email**, the way WD-60 names the
owner of the listing queue (`/api/devices/current` gives nothing else that
stays the same across pairings): `chrome.storage.local.watchdeskImportAnswers`
= `{ "<email>": "accepted" | "declined" }`.

## What is uploaded, and what is not

| Local data | Where it is | Carried over | How |
|---|---|---|---|
| Watches (URL, label, paused) | `chrome.storage.sync` `watches` | Yes | `POST /api/watches`, one per watch the account does not have by URL. A watch WatchDesk refuses (a site it does not take) stays in the browser and is counted. |
| Feed entries | `chrome.storage.local` `feed` | Yes: title, URL, posted label / date / approximate, salary, Easy Apply, workplace type | `POST /api/listings/ingest`, one watch per request, at most 200 a request. |
| **When the browser found a posting** (`detectedAt`) | on the feed entry | **No** | The route stamps `detected_at` with the server's clock and drops a `detectedAt` in the body (WatchDesk WD-57, decision 15). Imported listings are dated the day of the import. The posting's own date (`postedAt`) is kept. |
| "Applied" mark | on the feed entry | Yes, **for listings the import added** | `PATCH /api/listings/[id] { status: "applied" }`, one request per mark. The ingest answer names the server id only of the rows it inserted, so a posting the account already had is not marked; its own status (which may be "interviewing") is left. Counted as "not carried over". |
| When it was applied to (`appliedAt`) | on the feed entry | No | The route stamps `status_updated_at` itself. |
| "Read" mark (`visited`) | on the feed entry | No | It would be one more request per entry for a status ("viewed") that says little; left in the browser. Decision 9. |
| A feed entry whose watch is gone | `feed`, `watchId` of a removed watch | No, counted | A listing's site, owner and label come from the watch the request names; there is none to name. It stays in the browser's feed. Decision 8. |
| Check interval, alert sound, mute, keyword filter | `chrome.storage.sync` | Yes, **the ones the user stored** | One `GET` + `PUT /api/settings` through `account-settings.js`'s read-modify-write. A setting never stored (the extension's default applied) is not uploaded over the account's. One WatchDesk's limits refuse (more than 100 keywords) is left out and named; the others are saved. |
| Start / Pause Watching | `chrome.storage.local` `watcherState` | Not by the import | The settings PUT sends back the `watcherState` WatchDesk holds. WD-71's own report then tells WatchDesk this browser's state, as it always has. |
| Feed filters, seen ids, last check times | `chrome.storage.local` | No | Per-browser run state; no API field. |

**The local feed afterwards** is unchanged: still the popup's feed, still
capped at 20 per platform by `FEED_LIMIT_PER_PLATFORM`, with its marks. Its
entries carry the watches' WatchDesk ids from then on (WD-54's rule), and
later checks are sent by WD-59 as usual.

### What the API does not let the import carry over

For the main session to file against the web repository if wanted. Neither
blocks this ticket; both are said to the user in the card.

1. **Detection time.** `POST /api/listings/ingest` would need to accept an
   optional `detectedAt` (not in the future, perhaps only for a row it
   inserts) for imported history to keep its dates. Today every imported
   listing is "found today". WatchDesk WD-57's own follow-up says the same.
2. **A status for a listing the account already has.** Ingest answers with
   server ids only for inserted rows, and the extension has no route that
   finds a listing by `sourceKey` with a device token (this ticket did not
   look for one beyond the documents it was given). An ingest answer that
   named every row's id, or an ingest that accepted a status for new rows,
   would remove one request per applied listing too.

A note on scale: the handoff describes feed caps of 50 per platform and 500
for LinkedIn. **The code's cap is 20 per platform** (`FEED_LIMIT_PER_PLATFORM`,
`background.js`), so a browser holds at most about 80 feed entries and
"months of history" is, in practice, the latest 20 per site. The import is
built and tested for far more (730 entries across three watches) and does
not depend on the cap.

## How the import runs

In this order, because a feed entry can only be sent once its watch has an
id on WatchDesk:

1. **Watches** — `uploadOwnWatches()` in `watch-sync.js`: WD-54's first sync,
   bound to the import's connection. Each own watch is matched to the
   account's by URL or created; `carryRunState()` then moves seen ids and the
   feed entries' `watchId` to the server id.
2. **Listings** — the feed grouped by watch, at most 200 a request, sent
   straight to the ingest route. **Not through the WD-60 retry queue**, whose
   cap of 2,000 listings / 2 MB drops the oldest: what the import has sent is
   remembered in its own record (`sent`), nothing is queued.
3. **Applied marks** — one PATCH per listing the import added that was
   marked applied.
4. **Settings** — the stored ones, one read-modify-write.

**Pace.** One request at a time, 600 ms apart: at most 100 a minute, under
WatchDesk's 120 a minute per device, which the check cycle shares.
`authorizedRequest()` already waits out a `Retry-After` of up to 10 s; a
longer one stops the import until it is over.

**One bad row.** The route stores a batch whole or not at all. A 400 is
halved and each half sent, down to the single listing WatchDesk will not
take, which is left out and counted: about 2·log₂(n) extra requests, 15 for a
full batch of 200. Listings the extension can tell are unstorable (no id, no
title, a URL that is not http(s), a field over the route's limit) are fitted
or left out before anything is sent, by the same `toListing()` WD-59 uses.

**Resumable.** The record in `chrome.storage.local` holds the step, the feed
entries answered for, the marks still to make and the counts; nothing is in
a module variable. Every step is safe to repeat (watches match by id or URL,
the server upserts on `source_key`, a PATCH to the status a listing has
changes nothing). A worker stopped mid-request sends that one request again
and nothing else. An alarm (`watchdesk-import`, 30 s) wakes a stopped
worker, and the import also resumes on a check tick, on browser start and
when the popup opens.

**When WatchDesk cannot take a step** (unreachable, a 5xx, a 403, a 429
beyond 10 s) the import stops where it is, the card says why and where, and
it is tried again after the `Retry-After`, or after a wait that doubles from
one minute to thirty. **Retry now** does it at once. A 403 on a watch is an
unverified email; the card says to verify it.

**One at a time.** A second caller is handed the run already under way.

**Bound to one account (WD-110).** Every request carries the connection
captured when the run began, so it goes out with that token or not at all;
the run also checks that the connected account's email is the import's.
Progress is written through `changeImportRecord()`, the queue a new token is
stored in, and only while the stored record is still this import: a pairing
that completes replaces the record and the run ends without sending or
writing anything more.

## Decisions taken

The handoff said to proceed without stopping, so I took these myself. Each
is the option I would have recommended and is open to challenge at review.

1. **A pairing holds every sync, and the hold is one function.**
   `isAccountActive()` replaces `isConnected()` wherever a module picks its
   mode. While it is false the extension is in its unconnected code path,
   which is what "the watcher keeps working meanwhile, on the local list"
   means and why the unconnected parity tests cover it. The record is written
   with the token, so no worker stopped between two writes can leave a token
   without its hold.
2. **Only a real pairing writes the record.** A browser that was already
   connected has none and is not asked: it uploaded its watches long ago.
3. **"First" is per account email, remembered in this browser.** An account
   that answered is not asked again; a different account always is.
4. **"Not now" sets the watches aside rather than leaving them in the list.**
   The alternative that keeps them visible is a list that mixes the
   account's watches with ones WatchDesk does not have, which WD-54 already
   treats as an error state ("N watches are only in this browser"). Setting
   them aside keeps "the server's list is the truth" intact and loses
   nothing. A local watch whose URL the account has still becomes that watch
   (no upload is involved, and its seen ids are kept, so the next check does
   not announce old postings as new).
5. **Importing later is offered**, from Settings, because it was cheap: the
   same import with the set-aside watches added to the list and the settings
   read from WD-79's snapshot. While that question is open nothing is held:
   the browser is already working with the account.
6. **A declined account stays declined across reconnects.** Otherwise a
   disconnect before the first sync would upload everything the user had
   just declined.
7. **Only stored settings are imported.** Uploading the extension's defaults
   for settings the user never touched would overwrite what a second device
   or the web app had chosen, with nothing to restore it from.
8. **Feed entries without a watch are left out, not attached to another
   watch** of the same site: the listing would carry that watch's label,
   which the web's search matches on.
9. **Applied is carried, read is not**, and an existing listing's status is
   never overwritten. Cost: one request per applied listing, at most the
   feed's size (80 today), 600 ms apart.
10. **Imported listings are dated by WatchDesk.** Nothing in the request can
    change that; the card says so whenever a listing went up.
11. **Not through the WD-60 queue**, and no new endpoint.
12. **A stopped import retries by itself**, with a doubling wait, and its
    alarm is set for the end of the wait rather than left ticking.
13. **The import alarm is its own** (`watchdesk-import`), so a paused watcher
    (no check alarm, WD-71) still finishes an import.
14. **The card is a section under the account card**, not a dialog: the
    popup has no modal, and the question may stay open for days. Its text is
    a polite live region; the popup's one `role="status"` stays the sync line
    (WD-73). Buttons are plain buttons; the pressed one is not disabled while
    its answer is on the way (a browser takes the focus from a disabled
    button), and the focus is handed to the card's next button.
15. **`listWatches()` and `createWatch()` take an optional `connection`**, so
    the import's uploads are bound to one token like every other request of
    it. Without the argument they behave as before.
16. **No manifest change, no new permission.**

## Known limitations

- **Imported listings are dated the day of the import**, and "read" marks,
  applied dates and applied marks on listings the account already had are
  not carried over (above).
- **A worker stopped between WatchDesk storing a batch and the extension
  recording its answer** sends the batch again and is told nothing was new,
  so the applied marks of that one batch are not carried over (counted). The
  window is one storage write.
- **A watch created just before a worker is stopped** is found again by URL
  on the next try and counted as "already in your account" rather than
  "uploaded". The result is right; one count is off by the other.
- **A stopped import with the watcher paused and the popup closed** is
  retried by its own alarm only; that alarm is the import's, so it does run.
- **The hold needs the account's email.** If `/api/devices/current` keeps
  failing while the other routes work, the browser stays in its unconnected
  mode until it answers.
- **`chrome.storage.sync` is shared by the user's signed-in Chrome
  profiles** (WD-54, WD-79): a second browser on the same Chrome account
  shares the watch list and the settings, but not the record, which is in
  `chrome.storage.local`.
- **After "Not now", a browser's own watches are not in the popup's list**
  until imported (decision 4).
- **A different account is offered the last account's list and settings**
  along with the feed: by then they are what the browser holds.

## Manual verification (Chrome)

1. Load the repository root unpacked, pointed at a local WatchDesk
   (`WATCHDESK_ENV = "development"`; do not commit that). Add a watch or two
   and let a check find something.
2. **Connect Account** and approve. Reopen the popup: "Import your existing
   data" is under the account's email with your counts; the watch list is
   still your own and WatchDesk's Watches page is still empty.
3. Close the popup, wait for a check, reopen: the card is still there and
   WatchDesk still has nothing.
4. **Import**: the card counts up and ends with what was uploaded. WatchDesk
   shows the watches, the listings (dated today) and your settings.
5. On a second profile with data, connect the same account and choose **Not
   now**: WatchDesk is unchanged, the list shows the account's watches, the
   feed is as it was. Open ⚙: "Import this browser's data into your
   account…" is there; it asks again.
6. Stop the WatchDesk server and press **Import**: the card says it stopped
   and will be tried again. Start the server and press **Retry now**.
