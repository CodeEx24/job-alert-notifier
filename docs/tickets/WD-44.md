# WD-44 — One authenticated fetch wrapper for the WatchDesk API

**Epic:** EP-02 Extension Device Auth & Sync Protocol

## Overview

Every call the extension makes with its device token now goes through one
function, `authorizedRequest()` in `watchdesk-api.js`. It:

- attaches `Authorization: Bearer <token>`,
- retries network errors, 5xx and 429 with capped, jittered exponential
  backoff, honouring `Retry-After`,
- hands a 401 to one shared handler that discards the token and tells an
  open popup, which flips to "not connected" at once.

The job-check alarm now also confirms the connection, so a device revoked
on WatchDesk is noticed within one check interval even if the popup is
never opened.

Today the only token-carrying route is `GET /api/devices/current` (WD-45).
The wave-2 routes (watches, settings, ingestion) will plug into the same
wrapper.

## Acceptance criteria

- [x] Every WatchDesk API call attaches `Authorization: Bearer <token>`.
      — `authorizedRequest()` builds the header from the stored token on
      every attempt. `getCurrentDevice()` uses it. A static test fails if
      `Bearer` / `Authorization` appears in any other shipped file, or more
      than once in `watchdesk-api.js`. The pairing calls are deliberately
      unauthenticated and stay off this path (see decision 2).
      Tests: "attaches Authorization: Bearer <token>…", "builds the Bearer
      header in one place…", "the pairing calls stay off the authenticated
      path". In Edge: every attempt carried a Bearer header.
- [x] A 401 response clears the stored token and flips the popup to 'not
      connected'.
      — `discardToken()` in `account-connection.js` removes the token and
      the cached account, records the outcome `revoked`, and broadcasts
      `account-state-changed`. `popup-account.js` re-renders on it, so an
      **open** popup flips, and the next open reads "This browser was
      disconnected from your WatchDesk account." (WD-42's wording). Tests:
      "losing the connection…" (4), "on a 401, discards the token and tells
      an open popup…", "flips to not connected while open…". In Edge:
      revoking on WatchDesk flipped the open popup without a reload.
- [x] A network error or 5xx retries with exponential backoff up to a
      capped number of attempts before giving up for that cycle.
      — `RETRY_POLICY` (below). After the last attempt the caller gets the
      last answer: `getCurrentDevice()` reports `unreachable`, `error` or
      `rate-limited`, the token and account are kept, and the popup shows
      "Couldn't load the account details right now" if it has no email
      cached. The next check cycle asks again. Tests: "retries a network
      error and a 5xx with growing delays…", "gives up after maxAttempts…",
      "keeps the token … after retrying", "does not hold up the job check
      while WatchDesk is slow". In Edge: 503, 503, 200 → three attempts,
      gaps 974 ms and 1954 ms, connected.

## Decisions taken

The handoff said to proceed without stopping, so I took these myself. Each
is open to challenge at review.

1. **The wrapper lives in `watchdesk-api.js`, not `background.js`.** The
   ticket says "in background.js", but WD-42 made `watchdesk-api.js`
   (imported only by the service worker) the one API client, and CLAUDE.md
   says so. What the criterion needs is **exactly one authenticated path**,
   and that is `authorizedRequest()`. A static test enforces it.
   `account-connection.js` owns token storage and plugs in `getToken` and
   `onUnauthorized` with `configureAuth()` at load. This avoids a circular
   import, and `watchdesk-api.js` never touches `chrome.storage` itself.
2. **Pairing calls stay on `requestJson()`**: single attempt, no Bearer
   header, no 401 handling. They have no token, and the poll loop already
   paces itself (`pollIntervalSeconds`, `Retry-After`, 5 s after a failure).
   Retrying underneath it would multiply requests against WD-41's rate
   limits.
3. **Retry only what is safe to repeat.** GET and HEAD by default. Any
   other method gets one attempt unless the caller passes
   `idempotent: true`. That option is meant for a POST the server dedupes,
   such as a WD-59 ingestion batch with an idempotency key. Ingestion is not
   built here. A GET can opt out with `idempotent: false`.
4. **What is retried:** status 0 (network error, timeout, refused), 5xx and
   429. Other 4xx are never retried, and a 401 goes to the shared handler.
5. **`Retry-After` on 429/503 replaces the backoff**, but only up to 10 s.
   A longer one ends the call at once and the next cycle asks again (see
   the worker-lifetime note below). WatchDesk's 429s usually say a minute
   or more, so in practice a 429 means "give up for this cycle".
6. **Check the connection on every `check-jobs` alarm** (WD-42's
   follow-up). `refreshAccount()` starts in parallel with `runAllChecks()`
   and is awaited only after it, so it cannot delay or break the check.
   Its errors are swallowed, and it sends nothing when no account is
   connected. That is one `GET /api/devices/current` per interval (default
   5 min) per connected browser. **Check now** is unchanged and does not
   run it.
7. **The popup learns of a lost connection by a runtime broadcast**
   (`account-state-changed`, carrying the same state object the popup
   already gets, with no token). It does not use `chrome.storage.onChanged`,
   which would deliver the token's old value to the popup. Only extension
   pages receive `chrome.runtime.sendMessage`; content scripts would need
   `tabs.sendMessage`. With no popup open the call has no receiver, which
   is caught.
8. **The token is re-read before every attempt.** If a parallel 401 has
   already discarded it, the wrapper stops and answers 401 without sending.
   If a newer token has replaced it, the next attempt uses that one.
   `discardToken()` only drops the token that was actually refused (WD-42's
   rule, moved into the shared handler).
9. **Nothing new is logged.** Giving up is reported through the result,
   not the console.

## Retry policy

`RETRY_POLICY` in `watchdesk-api.js`:

| Setting | Value |
|---|---|
| `maxAttempts` | 4 (the first try plus 3 retries) |
| `baseDelayMs` | 1000 |
| `maxDelayMs` | 8000 (a cap; not reached with 4 attempts) |
| `maxRetryAfterMs` | 10000 |
| Request timeout | 15 s per attempt (`requestJson`, unchanged) |

The delay before retry *n* is `min(maxDelayMs, baseDelayMs · 2^(n-1))` with
"equal jitter": a uniform point between half of it and all of it. That gives
0.5–1 s, 1–2 s and 2–4 s. Each lower bound equals the previous upper bound,
so the waits always grow. The worst case is four 15 s timeouts plus about
7 s of waiting, roughly 67 s.

**MV3 worker lifetime.** The worker is stopped after about 30 s without an
extension API call or event, and a pending `setTimeout` does not count. The
wrapper reads the token from `chrome.storage.local` before every attempt.
That read is an extension API call, so the longest gap between such calls
is one request plus one wait, at most 15 s + 10 s = 25 s. This is also why
a longer `Retry-After` is not slept through. If the worker is stopped
anyway, the call is lost silently and the next alarm tries again. Nothing
depends on the call finishing.

## Implementation details

| File | What |
|---|---|
| `watchdesk-api.js` | `RETRY_POLICY`, `backoffDelayMs()`, `configureAuth()`, `authorizedRequest()`. `getCurrentDevice()` takes no token any more and uses the wrapper. `requestJson()` is unchanged. |
| `account-connection.js` | `discardToken()` (the one 401 handler: drops the refused token, outcome `revoked`, broadcast), `notifyStateChanged()`, `configureAuth(...)` at load. `refreshAccount()` no longer handles the 401 itself. |
| `background.js` | The `check-jobs` alarm listener also runs `refreshAccount()` alongside the checks. Nothing else changed. |
| `popup-account.js` | `initAccountCard()` listens for `account-state-changed` (new optional `messages` parameter, defaulting to `chrome.runtime.onMessage`). It never answers the message. |
| `CLAUDE.md`, `AGENTS.md` | The rule: every token-carrying call goes through `authorizedRequest()`. |

There are no new storage keys and no manifest change. The message
`{ type: "account-state-changed", state }` goes from the worker to extension
pages.

## API changes

None on the server. The extension still calls only WD-41's pairing routes
and WD-45's `GET /api/devices/current`. No routes were invented.

## Known limitations

- A browser restart clears `chrome.storage.session`, so after a restart a
  revoked browser shows plain "Not connected" without the reason. The
  token is still gone. This is WD-42's storage choice.
- A revoked device is noticed at the next check, up to one interval later
  (5 min by default), or at once when the popup is opened.
- A `Retry-After` longer than 10 s, and a non-idempotent request that
  failed, are not retried within the cycle. The caller sees the failure
  until the next one.
- If Chrome stops the worker mid-backoff despite the storage reads, that
  attempt is dropped without a trace (see above).

## Testing notes

`npm ci && npm run lint && npm test`: **124 tests in 5 files, all passing**
(87 before, so 37 new). Lint is clean, and `check-syntax` parses 12 of 12
files.

- `tests/watchdesk-api.test.js` covers:
  - **Header:** the Bearer header, the caller's other headers kept and a
    forged `Authorization` overwritten, `credentials: "omit"`.
  - **Retries:** network error and 5xx retried with growing gaps; given up
    after 4 attempts with the last answer returned and the token kept.
  - **No retry:** 400/403/404/409/422; 401 goes to the handler once,
    unretried; POST/PATCH sent once; `idempotent: true` / `false` honoured.
  - **Retry-After:** honoured on 429/503; backoff when it is absent; an
    over-long one ends the call.
  - **Token re-read:** before each attempt, and the call stops when the
    token is gone; the token never appears in a result.
  - **Jitter:** bounds, cap and monotonic growth.
  - **Single path:** the static check, plus pairing calls with no Bearer
    header and no retries.
- `tests/account-connection.test.js`:
  - **Failures keep the token:** offline after 4 attempts and through a 5xx.
  - **Requests:** Bearer on the real route; nothing sent when not connected.
  - **401:** an open popup is told (no token in the message); no popup open
    still works and the next open shows the reason; a newer token is kept;
    a 401 arriving mid-retries is honoured.
  - **Secrets:** no secret in any log or broadcast message.
- `tests/background-wiring.test.js`: the `check-jobs` alarm queries
  `/api/devices/current` with the token each time; nothing is sent when not
  connected; a hanging WatchDesk does not hold up the job check (`lastRunAt`
  written while the account check is still retrying); on a 401 the token is
  discarded, the popup is told, and the check still runs.
- `tests/popup-account.test.js`: the open card flips on
  `account-state-changed` and returns nothing; other messages are ignored.

**Mutation check.** Each of these made at least one test fail:

- the account check awaited before the job check,
- retrying non-idempotent requests,
- retrying 4xx,
- no Bearer header,
- ignoring Retry-After,
- out-of-bounds jitter,
- no broadcast,
- the popup ignoring the broadcast,
- discarding a newer token.

**In a real browser: 17 of 17 checks passed.** The setup was Microsoft Edge
(Chrome is not installed here) via Playwright, loading an unpacked copy of
this branch with `WATCHDESK_ENV = "development"`. The committed `config.js`
stays on production. It ran against a local WatchDesk (`wd-45-devices-list`
worktree, local Postgres, migrations applied, file outbox for email).

- Sign up and verify; pair; the popup shows "Connected to WatchDesk |
  <email> · Edge on Windows".
- With the worker's `fetch` patched to answer 503 twice, an account refresh
  made three attempts, all with a Bearer header, 974 ms then 1954 ms apart,
  and ended connected. The popup's answer held no token.
- Revoke the device on WatchDesk with the popup open. It stayed connected
  until the `check-jobs` alarm fired (brought forward to 1 s, period kept).
  Then the **open** popup flipped, without a reload, to "Not connected to
  WatchDesk | This browser was disconnected from your WatchDesk account."
  The token was gone, the outcome was `revoked`, `sync` was untouched, and
  the job check on that alarm still ran (`lastRunAt` updated).
- Reopening the popup showed the same reason and Connect Account. The
  existing controls render and the settings panel opens. The token was
  never in the popup DOM, and there were no page errors.

**Not verified in a browser:** Google Chrome itself; the production origin;
a real network outage or a real 5xx from WatchDesk (simulated in the worker
instead); a worker stopped mid-backoff; the real toolbar popup (opened as a
tab so it stays open).

## Manual verification (Chrome)

1. Load the repository root unpacked. For a local WatchDesk, set
   `WATCHDESK_ENV` to `"development"` and reload. Do not commit that.
2. Connect Account and approve, as in WD-42.
3. Keep the popup open. On WatchDesk's profile page, revoke this browser.
4. Wait for the next scheduled check (the "Check every" interval). The
   open popup turns into "Not connected to WatchDesk — This browser was
   disconnected from your WatchDesk account." Reopening the popup shows
   the same thing at once.
5. In the service worker console, `chrome.storage.local.get("watchdeskToken")`
   is empty.
6. Check that watches, Check now, Open all tabs, the settings panel and the
   feed behave as before.

## Follow-up tasks (wave 2)

- New token-carrying routes (watches, settings, ingestion) call
  `authorizedRequest()`. An ingestion POST passes `idempotent: true` only
  together with a server-side idempotency key (WD-59).
- If a wave-2 call needs to outlast the worker (a large upload), keep it
  alive explicitly or queue it in storage for the next alarm. The
  wrapper's 25 s budget per step is not enough for that.
- Consider persisting the "revoked" outcome in `local` so the reason
  survives a browser restart.
- A Disconnect button (from WD-42) should reuse `discardToken()`'s path.
