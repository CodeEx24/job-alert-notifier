# WD-117 — Imported listings keep the date they were first detected (extension half)

**Epic:** EP-11 · **Wave:** 4 · **Priority:** P1

## Overview

The import of a browser's own feed (WD-81) used to leave every listing dated
the day of the import, because WatchDesk stamped a listing with its own clock
and dropped any time the extension sent. WatchDesk's half of this ticket
(WatchDesk pull request #68) made `POST /api/listings/ingest` accept an
optional `detectedAt` per listing. **This is the extension half: the import
sends it.** Ordinary check cycles, and their retry queue, are unchanged and
send no time.

The contract is WatchDesk's `docs/tickets/WD-117.md`, section "For the
extension session". In short: `detectedAt` is an ISO 8601 date-time string
with an offset, on each listing; a number is a 400 that stores nothing; the
time is used only for a listing the request adds and only from 5 years back
to 5 minutes ahead of the server's clock; a time outside that is not an
error (the listing is stored with the server's clock); and when a request
sent at least one time, the answer has
`detectedTimes: [{ jobId, detectedAt, outcome }]` with `outcome` `"used"`,
`"out-of-range"` or `"kept"`.

## Decisions taken

Taken without stopping to ask, as the handoff instructed. Each is open to
challenge at review.

1. **The time is added in `local-import.js`, not in `toListing()`.**
   `toListing()` is `listing-ingest.js`'s and is what a check cycle and its
   queue send; the import calls it and then adds `detectedAt` to its own
   copy. So the check cycle cannot send a time by accident, and
   `listing-ingest.js` has no change at all.
2. **What counts as a time that can be sent** (`foundAt()`): a finite number
   greater than zero that `new Date()` can hold and writes in the 24-character
   form (`2026-09-30T08:15:30.123Z`). Everything else sends no field:
   missing, `null`, a string (even one that looks like a date: the feed
   stores a number, so a string is not this extension's), `NaN`, ±`Infinity`,
   zero, negative, beyond ±8.64e15, and **a number past the year 9999**. That
   last one is the only addition to the handoff's list: `toISOString()`
   writes such a date as `+010000-01-01T…`, which is not the form the
   contract names, and I could not read WatchDesk's validator to know it
   would not be a 400. It is a check of the form, not of the range: 1971 and
   the year 9000 are both sent, and WatchDesk says they are out of range.
3. **A posting this browser holds under two watches is sent with the
   earliest time that can be sent.** WD-82 already sends it for "the watch
   that found it first", by `Number.isFinite(entry.detectedAt)`. That test is
   now `foundAt()`, so an entry whose time is zero or negative no longer
   counts as the earliest. Otherwise such an entry would win and the posting
   would lose the real date the other entry has. This is the one change to
   WD-82's behaviour, and only for a feed entry with a time that is not a
   date.
4. **The report says how many listings were imported with today's date, in
   one line, and only when there are any**: "2 listings were imported with
   today's date: this browser had no date for them that your account
   accepts." It counts both reasons a new listing is dated today: WatchDesk
   answered `"out-of-range"` for it, or the extension had no time to send
   for it. One number, because to the user they are the same thing and the
   second would otherwise go unsaid. `"kept"` and `"used"` have no wording.
5. **The count is `counts.listingsDatedToday`, in all only, and absent while
   it is zero.** It is a part of `listingsNew`, not a seventh way a feed
   entry can end, so it is not in `bySite`, not in the table and not in the
   sums. It is not in `emptyCounts()`: a finished record with no such
   listing is byte for byte what WD-83 wrote, which is why none of WD-82's
   or WD-83's fixtures changed. The popup reads it with `whole()`, so a
   record without it, or with something that is not a count, shows no line.
6. **The sentence "WatchDesk shows imported listings as found today…" is
   gone from the report, for old records too.** A record finished by the
   extension before this change has nothing that tells it apart from a new
   one, and for a new one the sentence is false. Marking new records would
   have changed every finished record (and WD-83's fixtures) for the sake of
   a line; per WatchDesk's doc the account's `listings` table was empty when
   the import shipped, so such records are few or none. An old record
   renders as before but for that one line.
7. **The question says, before the choice, "Imported listings keep the date
   this browser found them. One your account already has keeps the date it
   has there."**, in place of WD-81's "…will be dated the day of the
   import…". The old sentence's "The date each job was posted is kept" went
   with it: it was there to soften the bad news.
8. **`ingestListings()` passes `detectedTimes` on only when WatchDesk sent a
   list**, each entry kept if it has a string `jobId` and a string `outcome`
   (an unknown outcome is kept; the import ignores it). With no list there
   is no key, so what a check cycle gets back is what it always got.
9. **No fallback for a server without the field**, as instructed.
10. **A time is never taken from `detectedTimes` back into the browser.** The
    feed keeps its own `detectedAt`; the answer is only counted.

## Known limitations

- **A request WatchDesk stored but whose answer never arrived** (the worker
  was stopped in between) is sent again and answered `"kept"`, so a listing
  dated today by the first try is not counted. WD-82's `listingsNew` has the
  same gap (it becomes `listingsExisting`).
- **A browser clock that was wrong when a posting was found** gives a wrong
  date, if it is inside WatchDesk's limits.
- **Listings imported before this change** stay dated the day of that
  import; importing again does not correct them (WatchDesk keeps a
  listing's first date). WatchDesk's doc, decision 11.
- **The report does not say which listings were dated today**, only how
  many.
- `docs/tickets/WD-81.md` (the table row on `detectedAt`, decision 10 and a
  known limitation) describes how it was before this ticket.

New: `tests/import-detected-time.test.js` (40 tests) and three in
`tests/watchdesk-api.test.js`.

**Existing tests changed on purpose: nine, in four files.** Each asserted
what this ticket reverses; no assertion about a count was touched.

- `tests/local-import.test.js`, "uploads the watches, then the feed…": the
  list of a sent listing's keys gained `detectedAt`.

  already has…": the assertion that a sent listing has no `detectedAt` was
  removed.
- `tests/import-confirmation.test.js`, "asks first, about the same data…":
  the sentence about dates in the question.
- `tests/popup-local-import.test.js`, six tests: the same sentence (three),
  and the report's "found today" line removed (three; one test renamed).

**Popup parity tests** (`tests/popup-parity-*.test.js`): none changed, none
added. The unconnected popup is unchanged.

**Broken on purpose, and tests failed:** the number sent instead of the
string (88 failures); the clock instead of the entry's time (21); zero and
negative times let through (4); a six-digit-year date let through (1); a
time added to `toListing()`, so a check cycle sends one (39);
`"out-of-range"` not counted (4); a `"kept"` listing counted as dated today
(1).

## Not verified

  WatchDesk. Everything above is Vitest: the real service worker and the

  written from WatchDesk's ticket doc, not from its code.

## Manual verification (Chrome)

1. Load the extension unpacked; let it check a few watches over more than
   one day (or set a feed entry's `detectedAt` back by hand in the worker's
   console).
2. Connect to a WatchDesk account that has none of those listings; answer
   **Import**.
3. On WatchDesk, the listings are dated when the browser found them, not
   today. In the worker's Network panel, each listing in
   `POST /api/listings/ingest` has `"detectedAt": "…Z"`.
4. No notification, tone or badge during the import.
5. Wait for a check: its `POST /api/listings/ingest` has no `detectedAt`.
