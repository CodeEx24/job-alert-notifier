# WD-59 — The check cycle posts its listings to WatchDesk

**Epic:** EP-06 Listings Ingestion & Retention · **Feature:** FT-0602 ·
**Wave:** 2 · **Priority:** P0

## Overview

Once the extension is connected to a WatchDesk account, every check cycle
also sends the listings it read to `POST /api/listings/ingest` (WD-57), so
they end up in the account without the user doing anything differently.

The check itself is untouched and comes first. Fetching, diffing, the local
feed, notifications, the badge and the sound are done and saved before the
first request is made, so WatchDesk being slow or down cannot make a check
late or lose one. A browser with no account connected sends nothing and
behaves exactly as it did.

The popup's existing sync line (WD-54) now also says when listings last
reached WatchDesk.

## Acceptance criteria

- [x] checkWatch()/runAllChecks() call the ingestion endpoint after each
      cycle's local detection logic runs.
      — `checkWatch()` returns the page's `jobs`; `runAllChecks()` returns
      `[{ watchId, jobs }]` for the watches it read, after it has saved the
      run state and raised the notifications, badge and sound. The alarm
      listener and `check-now` then call `sendCheckedListings()`, which posts
      them through `listing-ingest.js`. Tests: "posts the listings the cycle
      read, under the watch's server id, baseline included", "runs after the
      local detection: feed, notification and badge are done before the
      request is made", "Check now posts the listings too"
      (`background-wiring`); all of `listing-ingest`. In Edge: the request
      arrived at a local stub with the watch's server id and all four
      listings of the page.
- [x] A successful ingestion call is reflected in the popup's 'last synced'
      indicator.
      — A cycle whose listings all reached WatchDesk records
      `lastIngestedAt` in `chrome.storage.local`; the sync line reads
      "Watches synced with WatchDesk · just now · Listings last synced just
      now". Tests: "records when the listings last reached WatchDesk"
      (`listing-ingest`), "shows the result in the popup's state", "tells an
      open popup when the listings have been sent" (`background-wiring`),
      "describeWatchSync: when listings last reached WatchDesk" and "shows
      when listings last synced in the same line" (`popup-watch-sync`). In
      Edge: the line showed it after an alarm, and updated by itself in an
      open popup after Check now.

## Decisions taken

The handoff said to proceed without stopping, so I took these myself. Each
is the option I would have recommended and is open to challenge at review.

1. **What "last synced" means.** The line keeps two facts apart instead of
   merging them into one time, because they fail separately:
   - *Watches synced* — the last time this browser got the account's watch
     list (unchanged from WD-54).
   - *Listings last synced* — the last check cycle whose listings **all**
     reached WatchDesk.
   A merged "last synced" would say "just now" while every listing was being
   refused.
2. **A failed send is shown, not hidden.** When the latest attempt did not
   get everything through, the line turns amber and reads "Listings couldn't
   be sent to WatchDesk last time (last synced 1h ago)", keeping the time of
   the last success. While the watch list itself is offline, the offline
   wording stays and only "Listings last synced …" is appended.
3. **Where the call sits.** Not inside `runAllChecks()`'s body but
   immediately after it, in both callers. `runAllChecks()` returns what it
   read; the alarm listener awaits the send (so the worker stays alive until
   it is done), and `check-now` answers the popup first and sends
   afterwards. That makes "can never delay, block or fail a check" true by
   construction.
4. **Check now answers before the listings are sent.** Otherwise the popup
   would sit on "Checking…" for up to about 67 s when WatchDesk is not
   answering. The worker then sends `watch-sync-changed` and an open popup
   updates its line. The same message is sent after an alarm's cycle.
5. **Every listing on the page is sent each cycle**, not only the new ones,
   including the first (baseline) check of a watch, which shows nothing
   locally. WatchDesk keeps one row per posting and decides what is new.
6. **What is sent is what the title filter kept**, the same list the local
   detection works on. A posting the user's keywords filter out of the feed
   is not sent to their account either.
7. **A watch is named only by its server id.** `watch-sync.js` gained
   `getServerWatchIds()` (the ids recorded in `watchdeskWatchSync.serverIds`).
   A watch not uploaded yet, or refused by WatchDesk, is skipped this cycle
   and joins in after the sync that gives it a server id. Nothing is sent
   before this connection's first watch sync.
8. **Requests are one watch each, at most 200 listings, one at a time.**
   A page with more is split. Sequential, so that an outage is met once
   and not once per watch.
9. **The call retries** (`idempotent: true`, WD-44's policy: 4 attempts,
   Retry-After honoured up to 10 s). The server dedupes repeats, and nothing
   waits on the call.
10. **What each failure does:**
    - 401: the shared handler has discarded the token; stop.
    - 404: the watch was deleted on WatchDesk since the last sync. Its
      listings are dropped and the cycle carries on; not a failure.
    - 400: WatchDesk refused the batch. Sending it again would be refused
      again, so it is dropped; recorded as a failure; other watches still
      go.
    - Unreachable, rate limited, 5xx (after the retries): the rest of the
      cycle is not attempted; recorded as a failure.
11. **A failed batch is dropped, by design of this ticket.** WD-60 adds the
    queue. The seam is the `unsent` array in `runCycle()`
    (`listing-ingest.js`): the batches that failed for a reason that may
    pass, plus the ones not attempted after that, each `{ watchId, listings }`
    and ready to send as it is. A 400 is deliberately not in it.
    Until WD-60, a listing missed during an outage reaches WatchDesk only if
    it is still on the page at the next successful cycle.
12. **A listing WatchDesk could not store is left out here**, so that it
    cannot make WatchDesk refuse the whole batch: no id, no title, a URL
    that is not http(s), or a required field over WD-57's length limit. An
    optional field that is over its limit or the wrong type is sent as
    `null`. The limits are copied from WatchDesk's
    `lib/validation/listings.ts`.
13. **Nothing is sent for a watch that read no listings, or whose check
    failed.** Such a cycle leaves the record as it was.
14. **The record belongs to a connection.** `watchdeskListingSync` is removed
    whenever a token is stored or discarded, like `watchdeskWatchSync`.
15. **A new module, `listing-ingest.js`,** for the same reason as WD-54's:
    `background.js` is not linted, so it only routes.

## Implementation details

| File | What |
|---|---|
| `listing-ingest.js` (new) | `ingestCheckedListings(checked)` (never throws; resolves to `{ status, sent, unsent }`), `getListingSyncStatus()`, `toListing(job)`. |
| `watchdesk-api.js` | `ingestListings(watchId, listings)` → `{ kind: "ok", received, inserted }` or the same failure kinds as a watch call; `INGEST_MAX_LISTINGS`. |
| `watch-sync.js` | `getServerWatchIds()`. |
| `account-connection.js` | `LISTING_SYNC_KEY`, removed whenever a token is stored or discarded. |
| `background.js` | `checkWatch()` also returns `jobs`; `runAllChecks()` returns `[{ watchId, jobs }]`; `sendCheckedListings()`; `getSyncStatus()` adds `listings` to the popup's `watchSync`. |
| `popup-watch-sync.js` | `describeWatchSync()` reads `status.listings`; new tone `warning`. |
| `popup.js` | Listens for `watch-sync-changed` and re-renders the line. |
| `popup.css` | The `warning` tone shares the offline line's style. |

Storage:

| Area | Key | Shape |
|---|---|---|
| `local` | `watchdeskListingSync` | `{ lastIngestedAt: epoch ms or null, failed: boolean }` |

Nothing is kept in service-worker memory between cycles.

What the popup gets as `watchSync` when connected: WD-54's fields plus
`listings: { lastIngestedAt, failed }`. No token, no listing.

Field mapping (an adapter's job → WD-57's listing):

| Sent | From | When it cannot be sent |
|---|---|---|
| `id` | `job.id` (trimmed; a number becomes text) | listing left out |
| `title` | `job.title` (trimmed) | listing left out |
| `url` | `job.url` | listing left out |
| `postedRaw` | `job.postedRaw` | `null` |
| `postedAt` | `job.postedAt`, as `toISOString()` writes it | `null` |
| `postedApprox` | `job.postedApprox === true` | `false` |
| `salaryRaw` | `job.salaryRaw` | `null` |
| `easyApply` | `job.easyApply === true` | `false` |
| `workplaceType` | `job.workplaceType` if Remote / Hybrid / On-site | `null` |

Nothing else is sent: no site, source key, watch label or detection time
(WatchDesk derives those from the watch and its own clock).

There is no manifest change and no new permission.

## API changes

None on the server. The extension now also calls
`POST /api/listings/ingest` as documented in the WatchDesk repository's
`docs/tickets/WD-57.md`, with `{ watchId, listings }`.

## Known limitations

- **Production has no `listings` table yet.** Until its migration is
  applied, the endpoint cannot store anything. If it answers 5xx, every
  connected browser will make four requests per cycle and show the amber
  "Listings couldn't be sent" line. See "For the reviewer".
- **Listings missed during an outage are not re-sent** unless they are still
  on the page later (decision 11). WD-60.
- **The feed a browser already holds is not uploaded**, only what checks
  read from now on. WD-57 does not accept a `detectedAt`.
- **`inserted` is not used.** The extension still decides what to notify
  about locally.
- **A cycle with nothing to send leaves a previous "couldn't be sent" in
  place**, so the warning can outlast the outage until the next cycle that
  has listings.
- **Rate limit:** 120 requests a minute per device. One request per watch
  per cycle, so more than about 100 active watches on a 1-minute interval
  would reach it; the cycle then stops and reports the failure.
- **A hanging WatchDesk** keeps the worker busy for up to about 67 s after
  the check (four 15 s timeouts plus backoff). With a 1-minute interval the
  next cycle can start meanwhile; the two do not share state.
- **Length limits are copied from the server**, so a change there needs the
  same change in `listing-ingest.js`.
- `watch-sync-changed` is also delivered to the offscreen document, which
  ignores it.

## Manual verification (Chrome)

1. Load the repository root unpacked. For a local WatchDesk with the
   `listings` migration applied, set `WATCHDESK_ENV` to `"development"` and
   reload. Do not commit that.
2. Connect Account and approve. Reopen the popup: "Watches synced with
   WatchDesk · just now".
3. Click **Check now**. Within a moment the line adds "Listings last synced
   just now". The listings are in the account.
4. Stop the local WatchDesk and click **Check now**: "Done." appears at once
   and the feed updates as usual; a few seconds later the line turns amber
   (or "Offline", if the watch sync failed first).
5. Start it again and click **Check now**: the amber is gone and the line
   reads "Listings last synced just now" again.
