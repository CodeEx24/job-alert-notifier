# WD-79 — The extension's settings read and write through /api/settings

**Epic:** EP-10 · **Wave:** 4 · **Priority:** P0

## Overview

As a user, I want the extension's settings UI rewired to read/write through
/api/settings instead of chrome.storage.sync, so there is exactly one place
my settings actually live.

With a WatchDesk account connected, the check interval, the alert sound,
mute and the title-keyword filter are now the account's: loaded from
`GET /api/settings` when the popup and the settings panel open (and before
every check), and saved with `PUT /api/settings` when one is changed. The web
app's Settings page (WatchDesk WD-78) and the popup edit the same document.
With no account connected nothing changes: the settings are in
`chrome.storage.sync`, as shipped, and a line in the panel says so.

```
SETTINGS                                                            ✕
No WatchDesk account is connected, so the check interval, alert sound,
mute and keyword filter are saved in this browser only. Connect an
account at the top of this popup to keep them in WatchDesk.

SETTINGS                                                            ✕
The check interval, alert sound, mute and keyword filter are saved in
your WatchDesk account.
```

One pull request, this repository only. The API it calls (WatchDesk WD-56,
with WD-71's `watcherState`) is already merged and deployed.

## Field mapping

Every setting the popup edits, and where it lives once an account is
connected. The names and units are the same on both sides (WatchDesk's
`lib/settings.ts` was written from this extension's code), so no value is
converted; what differs is what WatchDesk refuses.

| Popup control | Message | Local key | API field | Conversion and limits |
|---|---|---|---|---|
| Check every (`#interval`) | `set-interval { minutes }` | `chrome.storage.sync` `intervalMinutes` (number of minutes) | `intervalMinutes` | None. WatchDesk takes 1, 5, 15 or 30 only; the popup offers exactly those. |
| Alert sound (`#sound`) | `set-sound { soundId }` | `soundId` | `soundId` | None. WatchDesk takes `default`, `chime`, `ping`, `alert`, `soft`, `none`: the six ids of `sounds.js`. |
| Mute desktop notifications | `set-notifications-muted { muted }` | `notificationsMuted` (boolean) | `notificationsMuted` | None. |
| Keyword filter: on/off, chips, Add | `update-title-filter { titleFilter }` | `titleFilter` `{ enabled, keywords: string[] }` | `titleFilter` `{ enabled, keywords }` | Same shape. WatchDesk trims each keyword, drops blanks and a keyword repeated in any letter case, then takes at most 100 keywords of at most 100 characters; the extension on its own only drops blanks. The popup shows what WatchDesk kept. `[]` is kept and means "filter nothing" on both sides. |
| Start / Pause Watching | `set-watcher-state` | `chrome.storage.local` `watcherState` | `watcherState` | WD-71, unchanged: this browser decides it and reports it; it is never read back. |

**Local-only, with or without an account** (not sent, and the panel's line
names only the four settings above):

| What | Where | Why it stays here |
|---|---|---|
| Feed search, platform, workplace, applied and sort choices | `chrome.storage.local` `feedFilters` | A view of this browser's feed; no API field. |
| The feed's size (`FEED_LIMIT_PER_PLATFORM = 20`) | a constant in `background.js` | Not a setting. WatchDesk keeps every listing and has no retention setting (product-owner ruling). |
| The per-platform list's open/closed state | popup memory | Not stored at all. |
| "Test" (plays the selected tone) | — | An action, not a setting. |
| The watch list, Pause All, per-platform Pause | `/api/watches` | WD-54, unchanged. |

The limits are in `settings-limits.js`, copied from WatchDesk's
`lib/settings.ts` and `lib/validation/settings.ts` with a comment naming
them. `tests/settings-limits.test.js` fails if the popup offers an interval
or a sound outside them.

## How it works

**One copy, read as before.** Connected, the four `chrome.storage.sync` keys
are the last-synced copy of the account's settings. `getSettings()` in
`background.js` is unchanged, so a check cycle reads its settings with no
request and keeps running on the last copy while WatchDesk is out of reach.
The copy is refreshed after every successful GET or PUT of the settings, and
at the points WD-54 refreshes the watch list: the popup opening, "Check now",
and every alarm tick (in parallel with the watch sync, so the check waits
once, not twice). Only a key whose value differs is written
(`chrome.storage.sync` rate-limits writes). Nothing that must survive a
worker restart is in a module variable.

**One writer.** `PUT /api/settings` replaces the whole document, which also
holds `watcherState`. Every write to it, the popup's and WD-71's report, is
`changeAccountSettings()` in `account-settings.js`: GET the settings as they
are now, change only the fields being changed, PUT them all back (including
any field this version does not know), both requests on one
`captureConnection()`. A settings save therefore sends back the watcher
state WatchDesk holds, never this browser's, and a Start/Pause report sends
back the settings WatchDesk holds, never the local copy. They run one at a
time under one lock, so of two quick changes the second is built on the
first's answer: last one wins, nothing lost.

**The interval and the alarm.** When the copy's interval changes because of
a sync, the alarm is re-armed on it with the first check a whole interval
away (a sync is often the start of a check; a second one must not start on
top of it). A user's own change re-arms it a few seconds away, as shipped.
Paused, no alarm is made.

### Messages

| Message | Answer |
|---|---|
| `sync-settings` (new) | `{ settings, settingsSync }`. Connected: after one GET into the copy. Not connected: this browser's settings, `{ mode: "local" }`, nothing sent. |
| `set-interval`, `set-sound`, `set-notifications-muted`, `update-title-filter` | Not connected: exactly as before (`{ ok: true }`, plus `titleFilter` for the last). Connected: `{ ok, error?, settings, settingsSync }` (plus `titleFilter`). |
| `get-state`, `check-now`, `set-watcher-state` | now also `settingsSync`: `{ mode: "local" }` or `{ mode: "account", lastSyncedAt, problem }`, `problem` being `null`, `"offline"` or `"unavailable"`. |
| `import-settings` | connected, may also carry `settingsError`. |

`settings` in an answer is `{ intervalMinutes, soundId, notificationsMuted,
titleFilter }` as the copy now stands. No answer holds the token.

### Storage

| Key | Area | Value |
|---|---|---|
| `intervalMinutes`, `soundId`, `notificationsMuted`, `titleFilter` | sync | Not connected: the user's settings, as before. Connected: the copy. |
| `watchdeskSettingsSync` | local | `{ lastSyncedAt, problem }`. Belongs to one connection: `account-connection.js` removes it whenever a token is stored or dropped. |
| `watchdeskSettingsBeforeConnect` | local | `{ takenAt, settings }` — see "For WD-81". |
| `watchdeskSettingsCopy` | local | The settings an account last gave this browser. Internal: it tells "the user changed a setting while disconnected" from "nothing changed". |

Nothing secret is in `chrome.storage.sync`; the token stays in
`chrome.storage.local` and is never logged or put in a message or the DOM.

### For WD-81 (importing local data)

`chrome.storage.local.watchdeskSettingsBeforeConnect`:

```json
{ "takenAt": 1759654800000, "settings": { "intervalMinutes": 15, "soundId": "alert" } }
```

- `settings` is what the four `chrome.storage.sync` keys held just before a
  connection's first successful load replaced them, exactly as stored. **A
  key that is missing was never stored**: the extension's default applied
  (5 minutes, `chime`, not muted, the default keyword list in
  `background.js`).
- `takenAt` is epoch milliseconds.
- It is kept through a disconnect and a reconnect. It is taken again at a
  later connection only if the user changed a setting while disconnected.
- Nothing in this ticket reads it, uploads it or removes it. To offer it,
  fill in the defaults and call `saveAccountSettings(settings)`, which checks
  it against WatchDesk's limits first; remove the key once the user has
  answered. Local settings were never validated, so a title filter kept here
  can exceed 100 keywords.

## Decisions taken

The handoff said to proceed without stopping, so I took these myself. Each
is the option I would have recommended and is open to challenge at review.

1. **The copy lives in the keys the worker already reads.** The model is
   WD-54's watch list: `getSettings()` and the check cycle are untouched,
   and after a disconnect nothing has to be moved back. The alternative, a
   separate copy in `chrome.storage.local`, would leave the pre-connection
   settings in place for WD-81 without a snapshot, but needs a second read
   path in the worker and a migration at every disconnect.
2. **A change made while WatchDesk is out of reach is refused, not queued**
   (the handoff's recommendation). A queued write that lands hours later
   replaces whatever was changed on the web in between; a visible refusal
   does not. The control goes back and the popup says why. Checks keep
   running on the last copy.
3. **After a disconnect the last copy stays as this browser's settings** (the
   handoff's recommendation), so nothing changes under the user. The 401
   that disconnects says so in the refusal, and the panel's line returns to
   "saved in this browser only".
4. **First connect: the account's settings win, the browser's are set aside,
   nothing is uploaded.** See "For WD-81". The snapshot is taken at the
   connection's first successful load or save, not at pairing, so a browser
   that connects while WatchDesk is unreachable keeps running on its own
   settings until the account's arrive.
5. **The read-modify-write moved out of `watcher-state.js` into
   `account-settings.js`**, and `watcher-state.js` now calls it. WD-71's
   tests pass unchanged. The watcher report still does not touch the copy
   ("never copies the account's settings into this browser" still holds for
   it); only a settings load or save does.
6. **Limits are checked in the worker, before any request, and shown in the
   panel.** The popup stays thin: it sends the change and shows the refusal
   (`settings-change-error` under the controls, and Settings' status line
   when the panel is open). A refused keyword stays in the box to be fixed.
   Limits apply only when connected; an unconnected browser accepts what it
   always did.
7. **A 403 and any other answer without settings is an outage, not a
   disconnect:** nothing changes, the token is kept, the line says WatchDesk
   couldn't give the settings. A 400 is WatchDesk answering: its field
   message is shown and the line is not turned into a warning.
8. **Reset Extension leaves a connected account's settings alone**, as it
   leaves its watches (WD-54). Resetting one browser should not put the
   settings of the web app and every other browser back to defaults. The
   hint, the confirm and the result line now say "Your watches and settings
   are kept". **This changes WD-111's connected wording and two parity
   assertions** (listed under Testing notes).
9. **Import, connected, saves the file's settings in the account** in one
   write, after the watches went in. If WatchDesk refuses them (a sound it
   does not know, too many keywords) the watches stay imported and the
   result says "The file's settings were not applied: …" in the error
   colour. WD-111's all-or-nothing rule for an unreachable WatchDesk is
   unchanged.
10. **Where the load runs:** popup open, panel open, a newly connected
    account, "Check now" and every alarm tick. No new polling (WD-80 owns
    live sync). Not on browser start: the first tick does it a few seconds
    later, as for watches.
11. **One attempt per request, 10 s each,** like the watch calls: a click
    should hear "offline" at once, and the load runs again on the next
    open or check anyway.
12. **Two new elements in `popup.html`,** both on `ADDED_SINCE_SHIPPED`:
    `settings-sync-note` (first line of the panel, `aria-live="polite"`; the
    popup's one `role="status"` stays the sync line) and
    `settings-change-error` (`role="alert"`, under the sound, because the
    interval and the sound are on the main page). `sync-settings` is on
    `SINCE_SHIPPED`. No manifest change, no new permission.

## Known limitations

- **A change made on the web shows up on the next popup open, panel open or
  check**, not live. Two edits to the same field are last-write-wins; the
  popup sends the whole keyword list it is showing, so a keyword added on the
  web after the popup loaded is replaced by the popup's next keyword change.
  WD-80.
- **`chrome.storage.sync` is shared by the user's signed-in Chrome profiles.**
  A second browser on the same Chrome account that is not connected to
  WatchDesk receives the copy as its own settings. WD-54 has the same
  property for watches.
- **Writes and loads wait their turn.** With WatchDesk hanging (not refusing),
  a load can wait behind a write in progress: at worst a check starts about
  30 s late, once. A WatchDesk that is simply down fails at once.
- **The copy is checked against the connection and then written in a second
  storage call**; a pairing completing between the two could leave one
  account's settings as the copy until the new account's first load, a moment
  later. The requests themselves cannot cross accounts. (WD-71 has the same
  gap.)
- **Reset does not reset the account's settings** (decision 8). There is no
  "defaults" button for them in the extension.
- **An account interval the popup does not offer** would leave "Check every"
  blank. WatchDesk only stores the four the popup has.
- **"Loading…" is shown for a connection's first load.** Later loads say
  "Checking it for changes…" after the sentence, since the copy on screen is
  already the account's.
- **An interval changed on the web** takes effect with the first check a
  whole new interval away, not immediately.

## Manual verification (Chrome)

1. Load the repository root unpacked, pointed at a local WatchDesk
   (`WATCHDESK_ENV = "development"`; do not commit that).
2. Open ⚙ with no account connected: the first line says the settings are
   saved in this browser only. Change the interval: it sticks, and nothing is
   sent.
3. Connect an account and open ⚙: the line says the settings are saved in
   your WatchDesk account, and the controls show the account's values.
4. Change the sound on WatchDesk's Settings page, then close and reopen ⚙:
   the popup shows it.
5. Change mute in the popup: the web Settings page shows it after a reload,
   and Start/Pause is as it was.
6. Stop the WatchDesk server and change the interval: it goes back, and the
   popup says WatchDesk can't be reached. "Check now" still works.
7. Revoke the device on WatchDesk and change a setting: the popup says the
   browser was disconnected and the line returns to "this browser only".
