# WD-54 — Extension watch list syncs through the WatchDesk API

**Epic:** EP-04 Watch (Link) Management · **Wave:** 2 · **Priority:** P0

## Overview

Once the extension is connected to a WatchDesk account, its watch list is
the account's. The popup's existing add, rename, pause and remove controls
call `GET/POST /api/watches` and `PATCH/DELETE /api/watches/[id]` (WD-52),
the same routes the web app uses, so a watch made on either side shows up on
the other.

`chrome.storage.sync`'s `watches` key stays, as the last-synced copy. The
check cycle, the popup and Open All Tabs read it exactly as before, so they
keep working when WatchDesk cannot be reached.

A browser with no account connected behaves exactly as it did.

## Acceptance criteria

- [x] The extension's add/edit/delete watch UI calls the same endpoints as
      the web app.
      — With an account connected, `add-watch` is `POST /api/watches`,
      `rename-watch` and `toggle-watch` are `PATCH /api/watches/[id]`,
      `remove-watch` is `DELETE /api/watches/[id]`, and Pause All / Resume
      All / per-site pause are one PATCH per watch that changes. All go
      through `authorizedRequest()`. Tests: "add, rename, pause and remove
      call WatchDesk's endpoints" (`background-wiring`), "changes while
      connected" (`watch-sync`), "the watch calls" (`watchdesk-api`). In
      Edge: each control produced the expected request at a local stub.
- [x] A watch added on the web appears in the extension popup within one
      sync/poll cycle.
      — The list is synced when the popup opens and on every `check-jobs`
      alarm before the check (decision 4). Tests: "brings a watch added on
      the web into the stored list", "syncs on the alarm before checking: a
      watch added on the web is checked on that very check". In Edge: it
      appeared on reopening the popup, and separately in storage after the
      next alarm with the popup untouched.
- [x] If the API is unreachable, the popup shows the last-synced list with a
      clear 'offline' indicator rather than an empty list.
      — A failed sync leaves the copy alone and sets `offline`; the popup
      shows "Offline — couldn't reach WatchDesk. Showing your watches as
      last synced 4m ago. They can't be changed until it's back." above the
      list. Tests: "while WatchDesk cannot be reached" (`watch-sync`), "the
      popup gets the last-synced list and an offline flag, never an empty
      list" (`background-wiring`), "shows a visible offline indicator above
      the watch list" (`popup-watch-sync`). In Edge: four watches and the
      offline line with the stub stopped.

## Decisions taken

The handoff said to proceed without stopping, so I took these myself. Each
is open to challenge at review.

1. **Two modes, decided by whether a device token is stored.** Not
   connected: nothing changes, the list lives in `chrome.storage.sync` and
   no request is sent. Connected: WatchDesk is the source of truth and the
   same `watches` key is its last-synced copy. I kept the key rather than
   adding a second list so that the check cycle reads what it reads today,
   and so that losing the connection leaves the user with the list they
   last saw.
2. **First connection uploads what the browser has, deduped by URL.** Every
   watch the browser did not get from WatchDesk is its own. If the account
   already has a watch with that exact URL, the local one becomes that
   watch and the account's label and paused state win. Otherwise it is
   uploaded with its label and paused state. Two local watches with the
   same URL are uploaded once. This includes the built-in default watch
   ("All OnlineJobs.ph postings"), because it is a watch the user is
   actually being alerted from. The side effect is that a new account
   gets that watch from its first browser.
3. **Local ids become server ids, and run state follows.** The copy stores
   the server's UUID as the watch id. `seenIds`, `lastChecked`, `lastResult`
   and `consecutiveErrors` are moved from the old id to the new one, and
   feed entries' `watchId` is updated, so an uploaded watch does not
   re-baseline. Feed entry ids are left alone.
4. **When it syncs:** on every `check-jobs` alarm, awaited before the
   check; on popup open; on Check now; and when the account card changes
   state while the popup is open. Before the check, so that a watch paused,
   deleted or added on the web takes effect on that very check. On popup
   open, so the list is fresh without waiting for an alarm; the popup
   renders the copy first and re-renders when the sync returns.
5. **A sync is one request with a 10 s timeout, not the WD-44 retry loop.**
   `listWatches()` calls `authorizedRequest()` with `idempotent: false`.
   The job check waits for the sync, and the retry policy can take about
   67 s against a server that accepts connections but never answers. The
   next alarm or popup open is the retry. Worst case the check starts 10 s
   late.
6. **Writes while offline are refused, not queued.** The popup shows
   "Can't reach WatchDesk, so your watches can't be changed right now. The
   list shown is the last one synced." and nothing changes locally. A queue
   would have to be replayed against a list that may have changed on the
   web meanwhile.
7. **Writes are sent once.** POST is not idempotent on the server
   (duplicates are allowed). PATCH and DELETE could be retried safely, but
   they come from a click, and a quick "offline" is better than a spinner
   through the backoff. No call passes `idempotent: true`.
8. **The copy changes only after WatchDesk agrees.** No optimistic update.
   The exceptions are answers that mean the watch is already gone: a 404 on
   DELETE removes it locally, and a 404 on PATCH removes it and says "That
   watch was already deleted on WatchDesk."
9. **How "deleted on the web" is told from "not uploaded yet".**
   `chrome.storage.local.watchdeskWatchSync.serverIds` records the ids this
   browser got from WatchDesk. A stored watch missing from the server's list
   is deleted if its id is recorded, and otherwise uploaded. The key is
   removed whenever a token is stored or dropped, so a reconnect, even to a
   different account, starts from "every watch is this browser's own" and
   never deletes anything.
10. **An empty account is shown as empty.** `getSettings()` used to
    substitute the default watch for any empty list. It still does, except
    once a connected account's list has synced.
11. **An unsupported URL is refused in connected mode.** WatchDesk answers
    400 and its message is shown; nothing is saved. Not connected, the
    extension still saves it with `siteId: null` (baseline §9.7, left
    alone).
12. **A local watch WatchDesk refuses (400) stays in this browser.** It is
    recorded in `rejectedIds`, not offered again, still checked locally, and
    the popup says "1 watch is only in this browser, not on WatchDesk."
    Dropping it could lose a working watch if the two repositories' host
    rules ever differ (WD-108 is changing the extension's).
13. **An upload that fails for another reason stops the uploads for that
    sync.** The remaining watches stay local and are offered again next
    time. If the POST reached WatchDesk but the answer was lost, the next
    sync matches the watch by URL instead of uploading it twice.
14. **Reset Extension keeps the watches when connected.** It does not delete
    them on WatchDesk, and resetting only the copy would be undone by the
    next sync. The confirm text says so. Not connected, it is unchanged.
15. **Import adds to the account when connected.** The imported list
    replaces the copy as before, then a sync matches each watch to the
    account by URL or uploads it, and brings the account's other watches
    back.
16. **A 401 on any watch call** goes to WD-44's shared handler: the token is
    discarded, the popup flips to not connected, and the list stays as the
    browser's own.
17. **The sync logic is a new module, `watch-sync.js`**, with the popup's
    line in `popup-watch-sync.js`. `background.js` and `popup.js` are not
    linted and have no unit tests of their own, so they only route to it.

## Implementation details

| File | What |
|---|---|
| `watchdesk-api.js` | `requestJson()` and `authorizedRequest()` accept a JSON `body`. New `listWatches()`, `createWatch()`, `updateWatch()`, `deleteWatch()`, each returning `{ kind, … }`. A list containing anything that is not a watch is an error as a whole. |
| `watch-sync.js` (new) | `syncWatches()`, `getWatchSyncStatus()`, `hasSyncedAccountWatches()`, `addAccountWatch()`, `updateAccountWatch()`, `setAccountWatchesEnabled()`, `removeAccountWatch()`, `forgetKnownWatches()`. One queue serialises every sync and change. |
| `account-connection.js` | `isConnected()`; `WATCH_SYNC_KEY`, removed whenever a token is stored or discarded. |
| `background.js` | The alarm and `check-now` sync before checking. The watch message cases route to `watch-sync.js` when connected. `get-state` and `check-now` also return `watchSync`. New `sync-watches` message. `getSettings()`, `resetExtension()` and `importSettings()` as in decisions 10, 14, 15. |
| `popup-watch-sync.js` (new) | `describeWatchSync()` (pure), `renderWatchSync()`, `renderWatchChange()`. |
| `popup.html` / `popup.css` | `#watch-sync-status` and `#watch-change-error` above the watch list, styled with existing tokens. |
| `popup.js` | Watch controls go through `changeWatches()`, which shows a refusal. `syncWatchesAndRender()` runs on open and when the account card changes state. The reset confirm text depends on the mode. |
| `popup-account.js` | `initAccountCard()` takes an optional `onState` callback. |

Storage:

| Area | Key | Shape |
|---|---|---|
| `sync` | `watches` | unchanged: `[{ id, siteId, url, label, enabled }]`. Connected, `id` is the server's UUID. |
| `local` | `watchdeskWatchSync` | `{ serverIds: string[], rejectedIds: string[], lastSyncedAt: epoch ms or null, offline: boolean }` |

What the popup gets as `watchSync`: `{ mode: "local" }`, or
`{ mode: "account", offline, lastSyncedAt, localOnly }`. No token.

There is no manifest change and no new permission.

## API changes

None on the server. The extension now also calls `GET /api/watches`,
`POST /api/watches`, `PATCH /api/watches/[id]` and
`DELETE /api/watches/[id]` as documented in the WatchDesk repo's
`docs/tickets/WD-52.md`. POST sends `{ url, label?, enabled? }` and never a
`siteId` or an `id`.

## Known limitations

- **A check cycle that overlaps a first-connection sync** can lose the
  moved run state for the uploaded watches, because `runAllChecks` writes
  back the whole run state it read at the start (baseline §9.10). The
  alarm's own sync finishes before its check, so this needs the popup to be
  opened mid-check. The effect is one re-baseline for those watches.
- **Dedupe is by exact URL.** A LinkedIn URL is normalised by both sides
  with the same rule today; if the two rules drift, a second browser could
  upload a duplicate.
- **`chrome.storage.sync` limits** (8 KB per item) apply to the copy as they
  did to the list (baseline §9.14). A list too large to store leaves the
  copy as it was and shows the offline line.
- **Chrome's own sync still replicates `watches`** between browsers signed
  in to the same Chrome profile. Two such browsers connected to different
  WatchDesk accounts would exchange lists.
- **A watch deleted on the web while this browser was disconnected** is
  uploaded again when it reconnects (decision 9).
- **Renaming a watch on the web** does not relabel its existing feed
  entries (baseline §9.9).
- **Pause All on more than 60 watches** would hit WD-52's update limit; the
  popup reports how many were not paused.
- Connecting does not sync by itself in the worker; the first sync is the
  next popup open, alarm, or the open popup noticing the card change.

## Manual verification (Chrome)

1. Load the repository root unpacked. For a local WatchDesk, set
   `WATCHDESK_ENV` to `"development"` and reload. Do not commit that.
2. Before connecting, add a watch. Connect Account and approve.
3. Reopen the popup: "Watches synced with WatchDesk · just now". On
   WatchDesk's Watches page the local watches are listed.
4. Add a watch on the web. Reopen the popup, or wait one check interval: it
   is in the list.
5. In the popup, add, rename, pause and remove a watch; each shows on the
   web after a reload.
6. Stop the local WatchDesk (or go offline) and reopen the popup: the list
   is still there under an "Offline" line; Pause shows the refusal.
7. Start it again and reopen: synced.
