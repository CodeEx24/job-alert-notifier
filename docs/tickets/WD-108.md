# WD-108 — Match a watch URL's site by exact domain or subdomain

**Type:** Bug · **Wave:** 2 · **Priority:** Low

## Overview

Each adapter's `hostMatch` in `sites.js` used `hostname.endsWith(domain)`, so
`notlinkedin.com` counted as LinkedIn. A host now matches a site only when it
is the site's domain or a dot-separated subdomain of it. WatchDesk's
`lib/sites.ts` gets the same change in its own PR (same key).

## Acceptance criteria

- [x] The extension's `sites.js` is changed the same way in
      `CodeEx24/job-alert-notifier`, with the same cases tested.
      — `isHostInDomain()` / `urlIsInDomain()` in `sites.js`, used by all four
      `hostMatch` functions and by the LinkedIn `normalizeUrl` host guard.
      `tests/sites.test.js` runs `tests/site-host-cases.json`, a byte-for-byte
      copy of WatchDesk's `lib/sites.host-cases.json` (33 cases, including
      `notlinkedin.com` and `linkedin.com.evil.example`).
- [x] Existing saved watches still resolve to their site (no regression for
      valid URLs).
      — "still matches every job-site host in the manifest and the adapters":
      every `host_permissions` entry, content-script match, `defaultUrl` and
      `tabQueryPattern` resolves to its site. A saved watch is looked up by
      its stored `siteId` first (`SITES[watch.siteId] || siteForUrl(...)`),
      which this change does not touch.
- The first criterion of the ticket (`lib/sites.ts`) is met in the WatchDesk
  PR.

## Decisions taken

Taken without stopping to ask, as the handoff instructed; open to challenge at
review.

1. **The rule is `hostname === domain || hostname.endsWith("." + domain)`**,
   in one helper instead of four copies of the `try`/`endsWith` block.
2. **A trailing dot is not matched** (`https://linkedin.com./…`). It was not
   matched before, and the manifest's host permissions do not cover it.
3. **Case-insensitive, by the URL parser** — `new URL()` lower-cases the
   hostname.
4. **Glassdoor country domains stay unsupported** (`glassdoor.co.uk`,
   `glassdoor.com.au`); the shipped extension never accepted them. They are in
   the table as refused.
5. **`normalizeLinkedInUrl`'s own host guard uses the same helper.** It is the
   same hostname rule, and leaving it loose would rewrite a look-alike URL if
   it were ever called directly.
6. **Nothing else changed**: no parsing, no storage, no popup, no manifest.

## Implementation details

| File | What |
|---|---|
| `sites.js` | `isHostInDomain()`, `urlIsInDomain()`; the four `hostMatch` functions and the `normalizeLinkedInUrl` guard use them. |
| `tests/site-host-cases.json` | The table shared with WatchDesk: `{ "url", "site" }`. |
| `tests/sites.test.js` | The table against `siteForUrl()` and every adapter's `hostMatch`; a coverage check on the table; the manifest check; the LinkedIn guard. |

## Known limitations

- A watch saved earlier on a look-alike host keeps its stored `siteId` and
  behaves as before (it fails every check, since the extension has no
  permission for that host). Importing such a watch from a backup file now
  skips it.
