# WD-60 — A failed ingestion call is queued and retried

**Epic:** EP-06 Listings Ingestion & Retention · **Feature:** FT-0602 ·
**Wave:** 2 · **Priority:** P1

## Overview

WD-59 sends each check cycle's listings to the connected WatchDesk account
and, when the call fails, records the failure and drops them. A listing that
had left the search page by the next successful cycle was lost.

Now the listings a cycle could not send wait in `chrome.storage.local` and
go out on the next cycle (the next alarm tick, or "Check now"), oldest first
and before that cycle's own. The queue is capped; when the cap drops
listings, the popup's sync line says so and how many.

The check itself is still untouched and still comes first. A browser with no
account connected has no queue and sends nothing.

## Acceptance criteria

- [x] A failed batch is kept in chrome.storage.local and retried on the next
      alarm tick.
      — `runCycle()` in `listing-ingest.js` queues what WatchDesk did not take
      (`watchdeskListingQueue`) and the next cycle sends the queue before its
      own listings. Tests: "is kept in chrome.storage.local, under the
      account it was read for", "is retried on the next cycle, before that
      cycle's own listings, and then leaves the queue", "is retried even when
      the next cycle read nothing" (`listing-ingest`); "keeps them in
      chrome.storage.local and sends them on the next alarm tick, before that
      tick's own", "Check now retries them too" (`background-wiring`). In
      Edge: a posting read during an outage, and gone from the page before
      WatchDesk came back, reached the stub on the next alarm.
- [x] The queue has a sane cap so a long outage doesn't grow storage
      unboundedly (oldest-first trim with a visible warning, not a silent
      loss).
      — 2,000 listings and 2 MB, whichever is reached first; the oldest are
      dropped and counted; the popup's sync line turns amber and reads
      "WatchDesk was out of reach for too long: the 42 oldest unsent listings
      were dropped". Tests: "drops the oldest listings over 2,000 and counts
      them", "keeps the queue under 2 MB when the listings are unusually
      long", the five "the dropped count" tests (`listing-ingest`); "warns
      that listings were dropped, and how many, even after everything else
      got through", "shows the dropped warning in every connected state",
      "shows dropped listings as a visible warning in the one sync line"
      (`popup-watch-sync`). In Edge: 2,042 listings were trimmed to 2,000 and
      the popup showed the line above.

## Decisions taken

The handoff said to proceed without stopping, so I took these myself. Each is
the option I would have recommended and is open to challenge at review.

1. **What is queued.**
   - Unreachable, timeout, 429, 5xx (after WD-44's retries): queued. So are
     the cycle's batches that were not attempted after the failure.
   - 401: the queue is kept, and what the cycle could not send joins it. It
     can go out only after the user reconnects (decision 2).
   - 400: never queued. A queued batch that gets a 400 is dropped and the
     failure recorded.
   - 404: that watch's queued listings are dropped, all of them, and the
     cycle carries on. Not a failure, as in WD-59.
2. **The queue belongs to an account, named by its email address** (trimmed,
   lower-cased), stored in the queue as `owner`. This is how "the same
   account" is known. `GET /api/devices/current` returns the account's email
   and display name and the device's id and label; a new pairing is a new
   device id, so the email is the only value that is the same before and
   after a reconnection.
   - The queue is read, sent and written only while the connected account's
     email equals `owner`.
   - It survives a refused token. `account-connection.js` no longer knows the
     account at that point, which is why the queue carries the name itself.
   - `refreshAccount()` removes it as soon as WatchDesk says the connected
     account is a different one (or has no email). That call runs right after
     pairing, on every alarm and when the popup opens.
   - Until WatchDesk has said whose a new token is, the queue is held and
     not sent.
   - **The extension has no "disconnect" of its own.** A browser stops being
     connected only when WatchDesk refuses its token. So the handoff's "on
     disconnect … the queue must be cleared" has no separate code path here:
     a refused token keeps the queue (as the handoff also asks), and it is
     cleared when a different account connects. If a Disconnect button is
     added, it should remove `watchdeskListingQueue`.
   - While the account's email is not known (the first call to
     `/api/devices/current` has not succeeded yet, or the account has no
     email), nothing is queued: a failed cycle is recorded and dropped, as in
     WD-59. Queueing without an owner could hand one account's listings to
     the next.
   - WatchDesk is a second guard: an ingest call for a watch that is not the
     caller's answers 404.
3. **Each listing is held once per watch.** The queue is a list of
   `{ watchId, listing }`, oldest first. Queueing a listing that is already
   there for the same watch replaces the old copy and puts the new reading at
   the end. A cycle's listing that got through also takes its older queued
   copy out.
4. **Order.** Queued listings first, then the cycle's own. Queued listings
   are grouped into requests by watch (at most 200 each), the watch with the
   oldest listing first.
5. **At most 10 queued requests per cycle** (`QUEUE_MAX_REQUESTS_PER_CYCLE`).
   Ten requests carry 2,000 listings, the whole cap, when they are one
   watch's; a queue spread over more than ten watches takes more than one
   cycle. The cycle's own requests are not counted and all go, as in WD-59.
   The first request that fails ends the cycle, so a cycle makes at most 10
   + one per watch + 3 retries, against WatchDesk's 120 a minute per device.
6. **The cap is 2,000 listings and 2 MB**, whichever is reached first
   (`QUEUE_MAX_LISTINGS`, `QUEUE_MAX_BYTES`). `manifest.json` has no
   `unlimitedStorage`, so `chrome.storage.local` allows about 10 MB for
   everything, including the feed and the seen ids. A listing is about 400
   bytes, so 2,000 is about 0.8 MB; at WD-57's length limits one is about
   3.4 KB, which is what the byte limit is for. With five watches each
   getting a few new postings an hour, 2,000 is several days of outage.
7. **Trimming is oldest first, as the ticket says.** Worth knowing: the
   oldest queued listings are the ones most likely to have left the page, so
   they are the ones a later cycle cannot read again. The alternative
   (dropping the newest, which are probably still on the page) would lose
   less, but it is not what the acceptance criterion asks for.
8. **The warning clears when the user has seen it and everything has since
   got through, both.** The handoff offered "seen" or "the next full
   success". Success alone would clear a warning overnight that nobody saw,
   which is the silent loss the ticket rules out. Seen alone would clear it
   mid-outage while more are being dropped. So:
   - the popup tells the worker when it has shown the count
     (`listing-drops-seen`);
   - if nothing is waiting and the last cycle did not fail, the count is
     cleared then; otherwise it is cleared by the first cycle that leaves
     nothing to send;
   - more drops after that add to the count and make it unseen again.
   "Seen" means the popup was open with the line showing. The line is above
   the watch list in the main view.
9. **The count shown is exact**, not rounded. The handoff asked for "roughly
   how many"; the exact number was no harder.
10. **One indicator.** The same line as WD-54 and WD-59. It adds "42 listings
    waiting to be sent" while the queue is not empty, and the dropped
    sentence in every connected state (synced, offline, still syncing).
11. **`lastIngestedAt` now means "nothing was left to send"**: the cycle sent
    everything and the queue is empty. A cycle that hit the 10-request bound
    without a failure leaves it unchanged and is not a failure either.
12. **A listing leaves the queue only after WatchDesk answered** 2xx (or 400
    / 404). If the worker stops between the answer and the storage write, the
    listing is sent again next cycle; WatchDesk keeps one row per posting.
13. **Cycles run one at a time**, through a promise chain in the worker. An
    alarm's cycle and "Check now" overlapping would otherwise both read the
    queue and send it twice. Nothing is kept in memory between cycles; a new
    worker starts a new chain.
14. **Every queue write re-reads the stored queue**, and is skipped once a
    different account is connected, so a cycle that was sending when the
    accounts changed cannot bring the old queue back or overwrite the new
    account's.
15. **The return value of `ingestCheckedListings()` is unchanged**
    (`{ status, sent, unsent }`); `sent` and `unsent` now include queued
    requests.

## Implementation details

| File | What |
|---|---|
| `listing-ingest.js` | The queue: `readQueue`, `updateQueue`, `enqueue`, `forget`, `forgetWatch`, `trimToCap`, `queuedBatches`; `runCycle()` sends queue then cycle; `inTurn()` serialises; `getListingSyncStatus()` adds `queued` and `dropped`; new `acknowledgeDroppedListings()`; exported `QUEUE_MAX_LISTINGS`, `QUEUE_MAX_BYTES`, `QUEUE_MAX_REQUESTS_PER_CYCLE`. |
| `account-connection.js` | `LISTING_QUEUE_KEY`; `getAccountOwner()`; `refreshAccount()` removes a queue owned by another account. The key is deliberately **not** in the lists removed when a token is stored or discarded. |
| `background.js` | Routes the popup's `listing-drops-seen` to `acknowledgeDroppedListings()`. |
| `popup-watch-sync.js` | `describeWatchSync()` reads `listings.queued` and `listings.dropped`. |
| `popup.js` | Sends `listing-drops-seen` after rendering a status with a dropped count. |

Storage:

| Area | Key | Shape |
|---|---|---|
| `local` | `watchdeskListingQueue` | `{ owner: "name@example.com", items: [{ watchId, listing }], dropped: number, droppedSeen: boolean }`. Absent while nothing is queued and there is no drop to report. |
| `local` | `watchdeskListingSync` | unchanged: `{ lastIngestedAt, failed }` |

What the popup gets in `watchSync.listings`:
`{ lastIngestedAt, failed, queued, dropped }`. Counts only: no listing, no
email, no token.

There is no manifest change and no new permission. `sites.js` is untouched.

## API changes

None. The extension calls `POST /api/listings/ingest` as before; a queued
batch is the same request.

## Known limitations

- **An account that changes its email on WatchDesk loses its queue** the next
  time the extension asks who it is, because the email is how the account is
  recognised (decision 2). A stable account id in `/api/devices/current`
  would remove this.
- **Nothing is queued until the account's email is known** (decision 2).
- **While disconnected, the popup shows nothing about a held queue**: the
  sync line is hidden with no account connected. The account card already
  says the browser was disconnected.
- **A 400 for a queued request drops up to 200 listings**, not only the one
  WatchDesk objected to. `toListing()` fits every listing to WD-57's limits
  before it is ever queued, so this needs a server rule the extension does
  not know.
- **If `chrome.storage.local` refuses the write** (quota), the cycle's unsent
  listings are lost and only the "couldn't be sent" line shows it. The 2 MB
  cap is there to keep that from happening.
- **A queue spread over more than ten watches drains over several cycles**
  (decision 5).
- **While WatchDesk is hanging**, each cycle spends up to about 67 s on one
  request before giving up, as in WD-59, and a "Check now" pressed meanwhile
  waits its turn to send. The check itself and the popup's answer do not
  wait.
- A listing still on the page is sent twice on recovery (once from the
  queue, once by the cycle). Harmless.

## Testing notes

`npm run lint` is clean (`check-syntax` parses 15 of 15 files) and
`npm test` passes **449 tests in 9 files** (392 before, so 57 new).

- `tests/listing-ingest.test.js` (+37): what is queued and after which
  failures; retry order; coalescing; the 10-request bound; splitting at 200;
  two cycles at once; removal only after a 2xx (a write that fails after the
  answer); 400 and 404 for queued batches; a 401 keeps the queue; nothing
  sent while disconnected; same account after reconnecting; a different
  account; an account not yet known; the account changing mid-cycle; both
  caps; the dropped count's lifecycle; no logging and counts only.
- `tests/account-connection.test.js` (+7): `getAccountOwner()`; the queue
  through a refused token, a refresh for the same and for a different
  account, an unreachable WatchDesk, and a new pairing.
- `tests/background-wiring.test.js` (+5): the next alarm tick and Check now
  retry; the popup state; `listing-drops-seen`; no queue when unconnected.
- `tests/popup-watch-sync.test.js` (+8): every wording and tone.

The requests go through the real `authorizedRequest()` over a mocked
`fetch`, as the existing suites do.

**Mutation check.** 27 deliberate breaks, one at a time. 26 failed at least
one test on the first pass; the 27th (writing the queue after another account
had connected) survived, got a test, and now fails it. Among the others: not
queueing, never retrying, the cycle before the queue, dropping the newest,
not counting drops, no request bound, no byte cap, using another account's
queue, not clearing it for a different account, dropping the queue on a 401,
unserialised cycles, clearing an unseen warning.

**In a real browser: 28 of 28 checks passed.** Microsoft Edge (Chrome is not
installed here) via Playwright, loading an unpacked copy of this branch whose
development origin pointed at a local stub. The stub served the API routes
and a search page in OnlineJobs.ph's markup. The committed `config.js` stays
on production.

- Not connected: the check ran, zero requests, no queue.
- Stub answering 500: the check still ran and the feed updated; four
  attempts; the page's four listings were in `watchdeskListingQueue` under
  the account's email; the popup read "… Listings couldn't be sent to
  WatchDesk last time (last synced just now) · 4 listings waiting to be
  sent".
- A second failed cycle, with the new posting gone from the page and another
  added: five listings queued, each once; only the oldest queued request was
  attempted.
- Stub back: the next alarm sent the queue, then the cycle; the posting that
  had left the page was stored; the queue key was gone; the popup read
  "Listings last synced just now".
- A 401 on ingest: token gone, the cycle's listings queued; the next check
  sent nothing; reconnecting as the same account sent them.
- A 401, then a different account: the queue was removed and its listing
  never reached the stub.
- 2,037 listings seeded, plus a failed cycle: trimmed to 2,000, 42 counted,
  the popup showed the warning and reported it seen; with the stub back the
  queue drained in one tick (10 requests of 200, then the cycle's own, about
  1.4 s) and the warning was gone.
- No page errors; neither the token nor a queued listing in the popup's DOM
  or `storage.sync`.

**Not verified:** the real WatchDesk API (production has no `listings` table
and the handoff said not to test against it); Google Chrome itself; the real
toolbar popup (opened as a tab so it stays open); a worker actually killed
mid-request (the unit test fails the storage write instead); a real network
outage (the stub answered 500).

## Manual verification (Chrome)

1. Load the repository root unpacked. For a local WatchDesk with the
   `listings` migration applied, set `WATCHDESK_ENV` to `"development"` and
   reload. Do not commit that.
2. Connect Account and approve. Click **Check now**: the line reads
   "Listings last synced just now".
3. Stop the local WatchDesk and click **Check now**. A few seconds later the
   line turns amber and ends with "N listings waiting to be sent" (or shows
   "Offline … N listings waiting to be sent." if the watch sync failed
   first).
4. Start WatchDesk again and click **Check now**: the line returns to
   "Listings last synced just now", and the listings read during the outage
   are in the account.

## For the reviewer

- Decision 2 (the email is the account's identity; no queue before it is
  known) and decision 8 (the warning needs both "seen" and a full success)
  are the two I would most expect to be challenged.
- Decision 7: the ticket asks for oldest-first trimming and that is what is
  built, though it drops the listings least likely to be readable again.
- **Outside this ticket's scope:** `/api/devices/current` gives no stable
  account id, so anything that has to recognise an account across pairings
  has to use the email. Worth a WatchDesk ticket.
- WD-59's release note still applies: production has no `listings` table
  yet. With this change a connected browser there would queue up to 2,000
  listings and then show the dropped warning, instead of only the amber
  line.
