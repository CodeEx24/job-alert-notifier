# WD-110 — Close three gaps in the listing queue

**Type:** Bug · **Wave:** 2 · **Priority:** Medium

## Overview

Three gaps found while reviewing WD-60 (PR #6), all in how
`listing-ingest.js` sends and queues a check cycle's listings.

1. **Mid-cycle loss.** A cycle's listings were queued only after a send had
   failed. A service worker stopped partway through the loop lost what it
   had not sent yet. They are now written to the queue before the first
   request and taken out as WatchDesk answers.
2. **Poison batch.** An answer the code had no rule for (413, 422, …) was
   treated like an outage: the cycle ended, and the same batch was tried
   first on every later cycle, for ever, with everything else behind it. Such
   an answer now skips that batch only, and after three attempts its listings
   are dropped and counted in the popup's existing "dropped" warning.
3. **Account-switch race.** The cycle checked whose listings they were, and
   the request then read the token separately. A pairing completing between
   the two could have carried one batch to the new account. Every request of
   a cycle is now bound to the connection the cycle started with: it goes out
   with that connection's token or not at all.

The check itself is untouched and still comes first. A browser with no
account connected has no queue and sends nothing.

## Acceptance criteria

- [x] The cycle's batches are written to the queue before the first send and
      removed as each is acknowledged. A test kills the loop midway and shows
      nothing is lost.
      — `runCycle()` calls `enqueue()` before the loop; `forget()` removes a
      batch after its answer. Tests (`listing-ingest-gaps`): "writes every
      batch to the queue before the first request, and takes each out as
      WatchDesk takes it", "a worker killed midway through the loop loses
      nothing" (first request answered, second never answered, module
      discarded, a new one sends the two that were left although their
      postings are no longer on the page), "a worker killed before the first
      answer loses nothing either".
- [x] A batch that keeps failing with a non-retryable or unknown status is
      dropped after a fixed number of attempts and counted in the visible
      "dropped" warning; it never blocks later batches.
      — `strike()` and `QUEUE_MAX_ATTEMPTS = 3`. Tests: "a 403 / 409 / 413 /
      422 does not end the cycle: the batches behind it still go", "never
      holds up the head of the queue", "is dropped after 3 attempts, counted
      in the dropped warning, and never sent again", "counts every listing of
      the batch", "keeps the count when the posting is read again", "an
      outage is not an attempt".
- [x] A batch can only be sent with the token of the account it was queued
      for. The owner is re-checked against the token actually used, or the
      request is bound to the owner. A test covers a pairing completing
      between the check and the send.
      — `captureConnection()` in `account-connection.js`, the `connection`
      option of `authorizedRequest()`. Tests: "between the owner check and
      the request reading the token: nothing is sent, and nothing is lost",
      and the same pairing landing before each of the first 80 storage reads
      of a cycle (a cycle of three watches makes fewer), plus between two
      batches, during a retry wait, and before the new account's name is
      known.

## Decisions taken

The handoff said to proceed without stopping, so I took these myself. Each is
the option I would have recommended and is open to challenge at review.

1. **A request is bound to a connection, not re-checked.** At the start of a
   cycle `captureConnection()` reads the token and the account's name in one
   storage call and returns a frozen `{ owner }`. `account-connection.js`
   remembers, privately, which token that handle stands for. The cycle passes
   the handle to `ingestListings()`, and `authorizedRequest()` asks for "the
   token of this connection" before every attempt, retries included. If the
   stored token is no longer that one, nothing is sent and the call answers
   `connectionChanged`. There is no window left to narrow: the token that
   goes out is, by comparison, the one whose owner was read.
   - `listing-ingest.js` still never sees the token.
   - A call that names no connection behaves exactly as before (same retry
     policy, Retry-After, 401 handling, and 401 for "no token"). The existing
     `watchdesk-api` tests pass unchanged and one new test pins it.
   - Reconnecting to the **same** account mid-cycle also ends that cycle. What
     is left is in the queue and goes out on the next one with the new token.
   - The loop's earlier owner check stays as a second guard.
2. **The account's name is kept in step with the token**, because decision 1
   relies on it at the moment of capture. Two gaps closed in
   `account-connection.js`:
   - `refreshAccount()` could store the answer to a request sent with one
     token after another token had been stored, leaving the old account's
     name beside the new token. It is now bound to its connection too, and
     the answer is stored (and the queue judged by it) only while that token
     is still the stored one.
   - `completePairing()` wrote the token and then removed the account in a
     second step. A worker stopped between the two would have left the new
     token beside whatever name was there. They are one write now.
3. **Write-ahead uses the queue itself.** The cycle's listings join the queue
   through the same coalescing as before (one copy per watch and listing id),
   so nothing is stored twice.
   - Order and request count are as in WD-60: what earlier cycles left goes
     first (at most 10 requests), then the cycle's own, all of them.
   - A listing that was waiting and is read again this cycle is sent once, in
     the cycle's own request, instead of twice. (WD-60 listed "sent twice on
     recovery" as a known limitation.)
   - While the account's email is not known there is still no queue, so
     there is no write-ahead either; the cycle's listings are sent directly,
     as in WD-59.
4. **The cap is applied when a cycle ends, not at write-ahead.** Applying it
   up front would drop the oldest waiting listings to make room for a cycle
   that WatchDesk then takes in full. So the queue may exceed the cap for the
   length of one cycle. A cycle that ends with anything unsent is trimmed
   exactly as before (oldest first, counted). A healthy cycle leaves no queue
   and trips no warning.
   - A worker killed mid-cycle can leave the queue over the cap until the
     next cycle ends. I first trimmed it at the next write-ahead as well; a
     mutation check showed that would drop listings WatchDesk was about to
     take, so it was removed.
5. **Which answers count as an attempt.**
   - Unreachable, timeout, 429 and 5xx: an outage. The cycle ends, nothing is
     counted, and the retry is unlimited as before (bounded by the cap). They
     say nothing about the batch.
   - 200: sent. 400: dropped at once, as before. 404: the watch's listings
     dropped, as before. 401: stop, queue kept, as before.
   - Anything else (403, 409, 413, 422, any other 4xx, a 3xx, a 2xx other
     than 200): one attempt against each listing of the batch; the cycle
     carries on with the next batch. At three attempts the listing is dropped
     and counted. Three, because one such answer can be a passing fault and
     attempts are a check cycle apart.
6. **The counter is per listing, stored on the queue item** (`attempts`,
   absent until the first). The queue holds listings, and batches are formed
   again each cycle, so a per-batch counter had nowhere stable to live. A
   newer reading of a posting keeps the count of the copy it replaces;
   otherwise a posting still on the page would start again every cycle and
   never be dropped. Only the listings that have had their three attempts
   are dropped, not the ones that joined the batch later.
7. **A cycle with such a batch is recorded as failed** (the amber "couldn't
   be sent" line), and the batch counts in `unsent`.
8. **`ingestCheckedListings()` still resolves to `{ status, sent, unsent }`.**
   A cycle ended by a changed connection is `not-connected`, as one ended by
   a 401 is.

## Implementation details

| File | What |
|---|---|
| `listing-ingest.js` | `runCycle()` captures the connection, writes the cycle ahead, sends bound requests, strikes a batch with an unruled answer and trims at the end. New: `strike()`, `trim()`, `isOutage()`, `attemptsOf()`, exported `QUEUE_MAX_ATTEMPTS`. `enqueue()` no longer trims and carries `attempts` over; `queuedBatches()` leaves out what the cycle read. |
| `account-connection.js` | New `captureConnection()` and the private `tokenFor(connection)` that `authorizedRequest()` now reads the token through. `refreshAccount()` is bound to its connection and stores the answer under the lock only for the same token. `completePairing()` writes the token and the emptied account together. |
| `watchdesk-api.js` | `authorizedRequest()` takes `connection`; `getCurrentDevice(connection)` and `ingestListings(watchId, listings, connection)` pass it and answer `{ kind: "connection-changed" }`. |
| `tests/listing-ingest-gaps.test.js` | New: the three gaps. |

Storage: `watchdeskListingQueue` items may now carry `attempts`
(`{ watchId, listing, attempts: 1 }`). A queue stored by WD-60 reads as
before. No other key changes; no manifest change; `sites.js`, `background.js`
and the popup are untouched.

## API changes

None. The same `POST /api/listings/ingest` and `GET /api/devices/current`.

## Known limitations

- **A batch that only ever gets a 5xx still holds the queue.** A 5xx is
  treated as an outage (decision 5), so a batch that makes WatchDesk fail
  every time ends each cycle at that batch. Telling it from a real outage
  needs either trying the next batch as well, which multiplies requests while
  WatchDesk is down, or a bound that would also drop listings during a long
  outage. Left for a decision.
- **The dropped warning's wording does not fit this cause.** It reads
  "WatchDesk was out of reach for too long: the N oldest unsent listings were
  dropped". For listings dropped after three refusals, WatchDesk was
  reachable and they need not be the oldest. The count is right; the sentence
  is in `popup-watch-sync.js`, which this ticket leaves alone.
- **A refused posting that stays on its page is dropped again every three
  cycles**, and counted each time, because every cycle reads the page afresh.
  The warning stays up while that goes on, which is true to what is
  happening, but the number grows.
- **Three refusals drop the listings that were in the batch** (up to 200),
  not only the one WatchDesk objected to, as with a 400.
- **A healthy cycle now writes the queue to storage** (once ahead, once per
  answer) where it used to write nothing. A few writes of well under 1 MB
  every check.
- **If `chrome.storage.local` refuses the write-ahead** (quota), the cycle
  sends nothing and is recorded as failed. Before, a healthy cycle did not
  depend on that write.
- **While the account's email is not known**, nothing is queued (WD-60), so a
  worker stopped mid-cycle still loses that cycle's unsent listings.

## Testing notes

`npm run lint` is clean (`check-syntax` parses 15 of 15 files) and `npm test`
passes **575 tests in 10 files** (449 in 9 before, so 126 new).

- `tests/listing-ingest-gaps.test.js` (110, new): write-ahead and removal on
  answer; a worker stopped midway and before the first answer; no double
  storing and no double sending; the cap not applied to a cycle WatchDesk
  takes, and applied to one it does not; unruled answers (403, 409, 413,
  422) skipping one batch; three attempts; counting; attempts surviving a
  re-read; outages not counted; a pairing completing at the request's token
  read, between batches, during a retry wait, before the new name is known,
  and before each of the first 80 storage reads of a cycle.
- `tests/watchdesk-api.test.js` (+8): a bound call sends with its
  connection's token, sends nothing once it has changed (also between
  attempts), and otherwise retries, honours Retry-After and reports a 401 as
  an unbound call does; an unbound call is unchanged.
- `tests/account-connection.test.js` (+8): `captureConnection()`; an account
  answer for a replaced or discarded token is not kept; the refresh is not
  retried with a newer token; the token and the emptied account are one
  write.
- `tests/listing-ingest.test.js`: one expectation changed. "stops a cycle
  when another account is connected while it is sending" expected no queue in
  storage afterwards; with write-ahead the old account's listings are still
  there under its own name, invisible to and unsendable by the new account,
  until `refreshAccount()` removes them. The test now asserts exactly that.

**Mutation check.** 24 deliberate breaks, one at a time, against the full
suite. 23 failed at least one test. The 24th (not trimming the waiting
listings at write-ahead) survived, and looking at why showed that the trim
was wrong (decision 4), so the code was removed and two tests added. Among
the 23: ignoring the connection at each of the four places it is passed, no
write-ahead, capping at write-ahead, no end-of-cycle trim, never dropping,
dropping at once, not counting, ending the cycle on an unruled answer,
restarting attempts on a re-read, counting each kind of outage, keeping an
account answer for a replaced token, and writing the token without emptying
the account. After that removal only the capping-at-write-ahead break was run
again (it still fails two tests); the other 22 were not.

**Not verified:** nothing was run in a real browser, and nothing against the
real WatchDesk API (the handoff rules production out). A worker is "killed"
in the tests by leaving its request unanswered and discarding the module, not
by Chrome stopping a real service worker. The change has no UI.

## Manual verification (Chrome)

1. Load the repository root unpacked, pointed at a local WatchDesk
   (`WATCHDESK_ENV = "development"`; do not commit that). Connect an account.
2. In the service worker's DevTools, put a breakpoint on the `fetch` call in
   `watchdesk-api.js` and press **Check now**. While it is paused on the
   request to `/api/listings/ingest`, `watchdeskListingQueue` in the
   extension's local storage holds the cycle's listings.
3. Resume. Once the check has finished the key is gone and the line reads
   "Listings last synced just now".

## For the reviewer

  `captureConnection()` in `account-connection.js`, and the few lines in
