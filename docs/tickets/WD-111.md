# WD-111 — Five popup and connected-mode fixes found by WD-72

**Type:** Bug · **Wave:** 3 · **Priority:** Low

## Overview

WD-72 proved popup parity and listed five things it found on the way
(`docs/tickets/WD-72.md`, "Found outside this ticket's scope"). This ticket
reproduces each one with a failing test against the real popup and the real
service worker, then fixes it. All five were real.

| # | Finding | Since | Fix |
|---|---|---|---|
| 1 | `getSettings()`'s URL migration writes `watches` itself, also when connected | WD-54 | Skipped while an account is connected |
| 2 | An import while WatchDesk is unreachable shows the file's watches as the list | WD-54 | Import asks WatchDesk first and imports nothing when it does not answer |
| 3 | The Reset hint says "Clears every watch" when connected | WD-54 | The hint says what Reset does in each mode |
| 4 | Mute, interval and sound do not update the popup's held state | shipped | The three handlers update it, as the keyword filter's always did |
| 5 | The install handler writes the settings back | shipped | The write-back is removed |

## What changes for a browser with no account connected

Items 4 and 5 are shipped behaviour, so this is the whole list:

- **Item 4.** After changing mute, the interval or the sound, the popup
  keeps showing the new value when it re-renders (opening a watch's Edit,
  for example), and **Export** straight afterwards writes the new value to
  the file. Before, both used the old value until the popup was reopened.
  The messages sent and the values stored are the same.
- **Item 5.** Installing or updating no longer writes `watches`,
  `intervalMinutes`, `soundId` and `notificationsMuted` to
  `chrome.storage.sync`. On a fresh install those keys now stay absent until
  the user changes something. Nothing the user sees depends on them being
  stored: `getSettings()` supplies the same defaults on every read, so the
  popup shows the default watch, 5 minutes and Chime as before, and the
  alarm is armed as before. What is gone is the overwrite: a value written
  between the handler's read and its write (the user's first change, or
  Chrome sync delivering another computer's watches and settings) was
  replaced by what the handler had read, which on a fresh install is the
  defaults.
- Items 1 to 3 change nothing here. The URL migration still runs and saves,
  Import and Reset are as shipped, and the hint's text is popup.html's own.
  `getSettings()` and `importSettings()` each make one more read of
  `chrome.storage.local` to see whether an account is connected.

## Decisions taken

The handoff said to proceed without stopping. Each of these is open to
challenge at review.

1. **Item 1: the migration is skipped, no API call is added.** WatchDesk
   normalises a URL when a watch is saved (`lib/sites.ts`), so it is the
   authority on a connected account's URLs and the extension uses them as
   stored: for the popup, for the check, for the tab it navigates. Sending a
   PATCH instead would need a route that accepts a URL change and would have
   two normalisers correcting each other. It is skipped for every watch
   while a token is stored, not only for ids WatchDesk gave: a watch that is
   still only in this browser was migrated before it was connected, and
   "never write `watches` directly in connected mode" then has no exception.
   The harm it removes is larger than "no effect yet" suggests: once the two
   rules differ, every read rewrites the copy and every sync puts it back,
   which is two `chrome.storage.sync` writes per popup open against a
   per-minute quota.
2. **Item 2: all or nothing.** A connected import asks WatchDesk for the
   account's list first. If it does not get it, nothing is imported: not the
   watches, and not the file's settings or the run-state reset either, so
   the user can simply import the same file again. The alternative was to
   keep the file's watches in the browser, marked as unsaved; that would
   keep hiding the account's own watches (and not checking them) for as long
   as WatchDesk is out of reach, which is the worse half of the bug.
3. **Item 2: where the user is told.** The outcome is in Settings' status
   line, where every import result already appears and where the user is
   looking. The cause is in the account card's sync line (the existing
   Offline state), which the worker refreshes with the existing
   `watch-sync-changed` message. No new indicator, element or message type.
   The handoff named the account card; the card says why, Settings says what
   happened to the file.
4. **Item 2: `forgetKnownWatches()` is replaced by
   `importAccountWatches()`.** The old path wrote the copy from
   `background.js` and then asked `watch-sync.js` to forget what it knew.
   The new one is a sync in which the file's watches stand in for the copy,
   under the same lock, and the copy is only written after WatchDesk
   answered. A successful import ends exactly as before: the file's watches
   matched by URL or uploaded, the account's others still listed, a watch
   WatchDesk refuses kept in the browser and counted as "only in this
   browser".
5. **Item 3: the paragraph gets an id, `reset-extension-hint`.** Listed in
   `ADDED_SINCE_SHIPPED` with a comment. Not connected, popup.js never
   writes to it, so the text is byte-for-byte popup.html's.
6. **The parity harness's WatchDesk now stores a LinkedIn URL the way the
   real one does.** "stores a LinkedIn search in its canonical, newest-first
   form" passed in connected mode only because the local migration rewrote
   what the fake had stored verbatim: it was asserting finding 1. The fake
   takes an optional `saveUrl`, the harness passes a copy of the server's
   rule, and the assertion is unchanged. Every other test file gets the old
   behaviour (stored as sent).
7. **Item 5: the write-back is removed, not narrowed.** Writing only the
   keys that are missing has the same race on a fresh install, where every
   key is missing. Nothing reads these keys without a default.

## Implementation details

| File | What |
|---|---|
| `background.js` | `getSettings()` skips `migrateWatchUrls` when connected. `importSettings()` calls `importAccountWatches()` first when connected, returns its refusal, and no longer writes `watches` in that mode. `onInstalled` only arms the alarm and records an update. |
| `watch-sync.js` | `runSync(imported)` returns WatchDesk's answer to the list request; `importAccountWatches(watches)` replaces `forgetKnownWatches()`. |
| `popup.html` | `id="reset-extension-hint"` on the existing paragraph. |
| `popup.js` | `renderResetHint()`; the mute, interval and sound handlers update `lastState.settings`. |
| `tests/popup-connected-fixes.test.js` (new) | 26 tests, one section per finding, through WD-72's harness. |
| `tests/watch-sync.test.js` | 10 tests of `importAccountWatches()` (one replaces the `forgetKnownWatches()` test). |
| `tests/helpers/fake-watchdesk.js`, `popup-harness.js` | `saveUrl` (decision 6). |
| `tests/popup-parity-markup.test.js` | The new id in `ADDED_SINCE_SHIPPED`. |

No message type, storage key, manifest entry or permission changed.

## API changes

None. An import makes the same requests as before (`GET /api/watches`, then
a `POST` per watch the account lacks), through `authorizedRequest()`.

## Known limitations

- **An import whose list request succeeds and whose uploads then fail**
  (rate limit, an unverified email, the network dropping in between) is as
  before: those watches stay in the browser, are offered again on the next
  sync, and the sync line says "N watches are only in this browser, not on
  WatchDesk."
- **A connected import that is refused applies none of the file's
  settings.** That is decision 2; someone who only wanted the settings has
  to wait for WatchDesk.
- **If WatchDesk ever stored a URL the extension cannot read** (the
  LinkedIn `/jobs/search-results/` shape), a connected browser would now
  check it as stored. Both sides apply the same rule on save today.
- **Item 5 in a real browser** was checked for the outcome (a value written
  as soon as the worker exists is still there, no defaults are stored), not
  by winning the race against the old code, which depends on timing.

## Testing notes

`npm run lint` is clean (`check-syntax` parses 17 of 17 files) and
`npm test` passes **1020 tests in 18 files, 9 skipped** (the 9 apply to one
mode only).

**Reproduced first.** Before any fix, `tests/popup-connected-fixes.test.js`
had 18 failing tests covering all five findings. Against the shipped copy
(`POPUP_PARITY_ROOT=<shipped copy>`), the 6 tests of items 4 and 5 that
apply to it failed too, so both are in the shipped extension.

**Parity.** `POPUP_PARITY_ROOT=<shipped copy> npx vitest run
tests/popup-parity`: 165 passed, 19 skipped, the same 165 as WD-72.

**In a real browser: 25 of 25 checks passed.** Microsoft Edge via
Playwright, an unpacked copy of this branch whose development origin pointed
at a local stub; the job sites were answered locally. The committed
`config.js` stays on production.

- Install: a setting written as soon as the worker exists is still there 3 s
  later; nothing else is in `chrome.storage.sync`; the alarm is armed; the
  popup shows the default watch, 5 minutes and Chime.
- Not connected: the Reset hint is the shipped text; interval, sound and
  mute keep their new values through a watch's Edit; nothing sent to
  WatchDesk.
- Connected: the hint says the watches are kept; a LinkedIn URL stored
  without `sortBy=DD` at the stub is still that URL in the copy and the
  popup after two more opens, with no PATCH; with the stub refusing
  connections an import shows the refusal, the Offline line and the
  account's three watches, and `chrome.storage.sync` is unchanged; with the
  stub back the same file imports, the watch is on the stub and in the list,
  and the file's settings are applied. No page errors; the token never in
  the DOM.

**Not verified:** the real WatchDesk app or its production origin (a stub
stood in; pairing was skipped by storing a stub token); Google Chrome itself
(Edge was used); the real toolbar popup (opened as a tab); Chrome sync
between two computers (the reason item 5 matters most); Export's file dialog
in a browser.

## Manual verification (Chrome)

1. Load the repository root unpacked. Change the interval, the sound and
   mute, then click a watch's **Edit**: the three controls keep their new
   values.
2. Open ⚙: under **Reset Extension…** the hint says "Clears every watch…".
3. Connect an account and open ⚙ again: the hint says the watches are kept.
4. Go offline and **Import…** a backup: Settings says nothing was imported,
   the account card says Offline, and the list is unchanged.
5. Go back online and import the same file: its watches join the account's.
