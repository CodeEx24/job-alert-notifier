# WD-71 — Start Watching / Pause Watching

**Epic:** EP-09 · **Wave:** 3 · **Priority:** P0

## Overview

As a user, I want Start Watching / Pause Watching buttons in the extension
popup, so I can stop the check alarm (e.g. overnight, or while job-hunting is
paused) without disabling every watch one by one.

The popup has one new control above "Check every":

```
● Watching is running                          [ Pause Watching ]
  Your watches are checked automatically.

● Watching is paused                           [ Start Watching ]
  No automatic checks until you start watching again. “Check now” still works.
```

Pausing clears the check alarm and records the state in this browser, so it
stays paused through a service-worker restart, a browser restart and an
extension update. Starting creates the alarm again on the user's interval.
No watch is changed either way. With a WatchDesk account connected the
account's `settings.watcherState` is told; with none, nothing is sent.

Two pull requests: the WatchDesk one adds `settings.watcher_state` and must
merge and deploy first. This one calls it.

## Acceptance criteria

- [x] Pause stops the periodic check alarm immediately and is reflected in
      settings.watcher_state server-side.
      — `setWatcherState()` in `background.js` saves `watcherState: "paused"`
      and `scheduleAlarm()` clears the alarm and creates none; then, after
      the popup is answered, `reflectWatcherState()` (`watcher-state.js`)
      GETs `/api/settings` and PUTs it back with only `watcherState` changed.
      Tests (`background-wiring`): "Pause clears the alarm at once, saves the
      state in this browser, and sends nothing" (not connected), "stays
      paused through everything that used to re-arm the alarm", "stays paused
      in a new service worker and after a browser restart", "a tick that was
      already on its way when the user paused checks nothing", "Pause is
      reflected in the account's settings.watcherState, and Start sets it
      back", "the click is answered before WatchDesk is…". Real browser
      against the real web app: Testing notes.
- [x] Start resumes it on the extension's normal interval.
      — The same `scheduleAlarm()`, no longer paused: `periodInMinutes` is the
      stored interval. Tests: "Start creates the alarm again on the user's
      interval, and the checks resume", "an interval chosen while paused is
      the one Start uses".
- [x] The popup clearly shows whether watching is currently running or paused.
      — `popup-watcher.js`: "Watching is running" / "Watching is paused" in
      words beside the button, and the status line under the controls reads
      "watching paused, no check scheduled" in place of the countdown. Tests
      (`popup-watcher`): "says in words that watching is running…", "says in
      words that watching is paused…", "names the state in text, not by
      colour alone".

## Decisions taken

The handoff said to proceed without stopping, so I took these myself. Each is
the option I would have recommended and is open to challenge at review.

1. **A new state, not Pause All.** The shipped extension had no running /
   paused concept for the alarm: Pause All sets `enabled: false` on every
   watch (and, connected, PATCHes each one on WatchDesk). "Running" in the
   settings backup and the baseline document refers to those. The ticket
   asks for the opposite — stop checking without touching the watches — so
   this is `watcherState`, and Pause All is unchanged.
2. **Kept in `chrome.storage.local`, not `chrome.storage.sync`.** The alarm
   belongs to one browser; a synced flag would say "paused" in a second
   browser whose alarm is still running until something there read it.
   Missing means running, which is what every installed copy is today.
3. **This browser is the authority; WatchDesk is told, never asked.** The
   state is not read back from the account, and no other setting is synced
   (wave 4). A browser that connects reports its own state, even over a
   different one already on the account.
4. **`scheduleAlarm()` is the one gate.** It was already the only place the
   alarm is created; it now creates none while paused. Install, update,
   browser start, "Check every", Reset, Import and the self-heal all come
   through it, so none needed its own check. `ensureAlarmScheduled()` clears
   an alarm it finds while paused (a worker stopped between saving the pause
   and clearing the alarm), and the alarm listener ignores a tick that was
   already queued.
5. **"Check now" still works while paused.** It is an explicit action, and
   the popup says so. It does not bring the alarm back.
6. **Start checks a few seconds later, then on the interval** — the existing
   `delayInMinutes: 0.1`, as after any other re-arm. Asking for the state
   the browser is already in changes nothing, so a repeated click does not
   restart the countdown.
7. **Reset Extension starts watching again** (it puts every setting back to
   its default). **Import leaves the state alone**: the backup file has no
   such field and `popup.js`'s export was not changed.
8. **WatchDesk is told after the click is answered.** The handler saves,
   deals with the alarm, answers the popup, and only then sends. A WatchDesk
   that never answers costs the user nothing.
9. **GET then PUT, one attempt each, 10 s each, on one `connection`.** PUT
   replaces every setting, so the whole object just read is sent back with
   one field changed, including any field this version does not know. No
   retry loop: it runs again on every sync anyway. Both requests carry the
   `captureConnection()` taken at the start (WD-110), so settings read from
   one account cannot be written to the account that connected next, and the
   result is recorded only while that connection is still the stored one.
10. **A failed report is retried on the next sync**: when the popup opens
    (`sync-watches`), on "Check now", after each alarm tick, and at browser
    start. `watchdeskWatcherSync` holds the state the account was last given;
    there is nothing to send while it matches. It is removed with the token,
    so a new connection is told afresh.
11. **Success is checked, not assumed.** The PUT's answer must hold the state
    that was sent. A WatchDesk deployed without WD-71 drops the unknown key
    and answers 200; that is recorded as a failure, not as told.
12. **The failure is shown in the existing sync line** (as the handoff asked):
    "… · WatchDesk hasn't been told that watching is paused yet; it will be
    sent again", in the warning tone, as `watchSync.watcherUnsent`. It is
    shown only after an attempt has failed, not during the first one.
13. **One control, one button.** The ticket says "buttons"; the popup has one
    whose label is the action available — "Pause Watching" while running,
    "Start Watching" while paused — next to a line that states the current
    state. Two buttons with one always disabled would say the same with more.
    Starting is the primary-coloured button; pausing is the quiet one.
14. **`aria-live="polite"`, not `role="status"`,** on the state line. WD-73
    (merged while this was in progress) asserts the popup has exactly one
    `role="status"`, the sync line. The state line is announced the same way
    the account title is.
15. **Popup footprint kept small** for the tickets editing it in parallel:
    one `<section>` in `popup.html`, one CSS block, and in `popup.js` an
    import, one render call, one init call and a paused clause in
    `renderCheckStatus()`. `sites.js` is untouched.

## Implementation details

| File | Change |
|---|---|
| `watcher-state.js` (new) | `getWatcherState`, `isWatchingPaused`, `saveWatcherState`; `reflectWatcherState` (the report to WatchDesk, serialised, never throws); `getWatcherSyncStatus` |
| `background.js` | `scheduleAlarm` / `ensureAlarmScheduled` / the alarm listener respect the state; `setWatcherState`, `sendWatcherState`; message `set-watcher-state`; `watcher` in the popup state and `watcherUnsent` in `watchSync`; Reset |
| `watchdesk-api.js` | `readSettings`, `replaceSettings` through `authorizedRequest()` |
| `account-connection.js` | `WATCHER_SYNC_KEY`, removed wherever a token is stored or dropped; `isCurrentConnection()` |
| `popup-watcher.js` (new), `popup.html`, `popup.css`, `popup.js` | the control |
| `popup-watch-sync.js` | the "hasn't been told" clause |

### Messages

| Message | Answer |
|---|---|
| `set-watcher-state` `{ state: "running" \| "paused" }` | the popup state (as `get-state`), or `{ ok: false, error: "Unknown watcher state" }` |
| `get-state`, `check-now` | now also `watcher: { state }`, and in account mode `watchSync.watcherUnsent`: `"paused"`, `"running"` or `null` |

### Storage (`chrome.storage.local`)

| Key | Value |
|---|---|
| `watcherState` | `"running"` \| `"paused"`; missing is running |
| `watchdeskWatcherSync` | `{ sent: "running" \| "paused" \| null, failed: boolean }`; belongs to one connection |

Neither holds the token, and the account's settings are never stored.

## API changes

None here. Calls `GET` and `PUT /api/settings` (WatchDesk `docs/tickets/WD-56.md`
and `WD-71.md`) with the device token.

## Known limitations

- **While paused, a failed report waits for the user or a browser start.**
  There is no alarm tick to retry on, and none was added: a paused extension
  that wakes itself to phone WatchDesk is not what "paused" should mean. The
  account says "running" until the popup is next opened.
- **One state per account on WatchDesk, one per browser here.** Two browsers
  on one account each report their own; the account shows the last report.
- **WatchDesk cannot pause a browser.** Nothing reads the state back.
- Import does not carry the state (decision 7).
- An alarm tick already running when Pause is clicked finishes its check; a
  later one does nothing.
- The record is checked against the connection and then written in a second
  storage call; a pairing completing between the two could leave the new
  connection believing it had been told. The next change of state corrects
  it. (The requests themselves cannot cross accounts.)

**In a real browser, against the real web app: 14 of 14 checks passed.**

loading an unpacked copy of this branch whose development origin pointed at
the WatchDesk WD-71 branch's dev server on a local Postgres with its

## Manual verification (Chrome)

1. Load the repository root unpacked, pointed at a local WatchDesk that has
   WD-71 (`WATCHDESK_ENV = "development"`; do not commit that).
2. Open the popup: "Watching is running" and **Pause Watching**; the status
   line counts down to the next check.
3. Press **Pause Watching**: "Watching is paused", **Start Watching**, and
   the status line says "watching paused, no check scheduled". At
   `chrome://extensions` → service worker console,
   `await chrome.alarms.get("check-jobs")` is `undefined`.
4. Restart Chrome and reopen the popup: still paused. **Check now** still
   checks.
5. Connect an account and press Pause, then Start: `GET /api/settings` on
   WatchDesk shows `"watcherState": "paused"`, then `"running"`.
6. Stop the WatchDesk server and press Pause: it pauses at once, and the
   account card soon says WatchDesk hasn't been told. Start the server and
   reopen the popup: the warning goes.
