# WD-80 — A setting changed on one side shows up on the other within one sync cycle

**Epic:** EP-10 · **Wave:** 4 · **Priority:** P1

## Overview

As a user, I want a setting I change on the web to show up in the extension
(and vice versa) within one sync cycle, so I never have to wonder which side
has the 'real' value.

Most of this was already true after WD-79: every alarm tick fetched the
account's settings before it checked, and every change in the popup was a
PUT. This ticket found what was missing and built only that:

1. **An open popup did not follow a check.** The worker fetched the new
   settings and checked on them, while the popup went on showing the old
   ones until it was reopened. The worker now tells it.
2. **A keyword change sent the popup's whole list.** A keyword added on the
   web after the popup loaded was removed by the popup's next keyword change
   or by turning the filter on or off. The change is now applied to the
   filter the account holds at that moment.
3. **Nothing proved the rest.** Each setting, in each direction, with the
   popup closed, with a new service worker, paused, failing, and behind the
   import question, now has a test.

One pull request, this repository only. No API change, no manifest change,
no new permission, no new request.

## Acceptance criteria

- [x] A setting changed on the web is picked up by the extension on its next
      poll/check cycle without requiring the popup to be reopened.
      — The alarm listener fetches `/api/settings` before `runAllChecks()`
      (`syncSettingsBeforeCheck()`, `background.js`), so the check that tick
      runs uses the new values: the alarm is re-armed on a new interval, the
      notification uses the new sound and mute, the detection uses the new
      filter. Nothing depends on the worker having stayed alive. If the
      popup is open, the worker sends `settings-changed` and the controls
      change in place. Tests: `tests/settings-two-way.test.js`, "a setting
      changed on the web is picked up on the next check cycle, with the
      popup closed" (each setting, twice: worker still running, and a new
      worker started by the alarm) and "with the popup open, a check that
      brings a change updates the controls". Real browser: Testing notes.
- [x] A setting changed in the extension is visible on a web page refresh.
      — Every change is `GET` then `PUT /api/settings` through
      `changeAccountSettings()`, confirmed by WatchDesk's answer, which is
      what this browser then keeps. Tests: "a setting changed in the
      extension is in the account for the web page's next load" (each
      setting; the PUT body is the document WatchDesk held at that moment
      with one field changed). **The web half is not this repository's and
      was not run here:** WatchDesk's Settings page (WD-78) loads the
      settings with `GET /api/settings` in the browser when the page loads,
      and again whenever the window gets the focus back, so a refresh shows
      what the PUT stored. That is read from `WD-78.md`, not observed.

## What "picked up on the next cycle" means, point by point

- **Order.** `prepareImportOffer()` → watches and settings fetched together
  → `runAllChecks()`. The settings GET is before the job-site fetch in the
  request log ("the settings are fetched before the check, never after it,
  with one request"). Moving it after the check fails 22 tests.
- **A worker that was asleep.** The alarm starts it; the listener is the
  same code. Every test of the first table runs a second time with the
  worker's modules loaded afresh between the web change and the tick, on the
  same storage. Nothing a cycle needs is in a module variable.
- **The interval and the alarm.** One `chrome.alarms.create` per change,
  none on the cycle after, none while paused.
- **How long is one cycle.** At most the interval the browser is on when the
  change is made: 1, 5, 15 or **30 minutes** at the longest setting, plus
  however late Chrome fires the alarm (a closed browser or a sleeping
  computer fires it on waking). The one case a user can notice is shortening
  the interval on the web from 30 minutes: it takes effect at the next tick
  of the old interval, so up to 30 minutes. The other four settings only act
  during a check, so "at the next check" is the earliest they could matter.
- **No separate poll** (decision 1).
- **Paused.** No alarm, so nothing is fetched and nothing is used. Start
  Watching checks a few seconds later, and that check fetches first: "Start
  Watching: the first check fetches the settings changed meanwhile and the
  alarm ends on the new interval". Opening the popup fetches too (WD-79).
- **A refresh that fails** (offline, 403, 404, 429, 500, a body that is not
  settings): asked once, the copy and the alarm stay, the check runs on the
  settings last loaded, the token is kept, and the cycle after WatchDesk is
  back has the change. A 401 drops the token and the copy becomes this
  browser's own settings, as WD-79 decided; the check still runs.
- **The import question** (WD-81): while it is unanswered no settings
  request is made and the browser's own settings are used.
- **Request cost.** Unchanged: one `GET /api/settings` per tick, which WD-79
  already made. No PUT unless the user changed something.

## Conflicts: what is and is not solved

A save is still "read the document, change a field, PUT the whole document"
with no version check (WatchDesk WD-56, "No optimistic concurrency"). A save
made on the web between this browser's GET and its PUT is overwritten by the
PUT. That window is one request long. **Nothing in this ticket closes it, and
nothing here pretends to**: it needs the server.

What the extension does on its own, all of it in `account-settings.js`:

- every PUT body is built in one place, from the document just read, with
  only the fields being changed (WD-79);
- a keyword change is now a change to the account's current filter, not the
  popup's list over it (this ticket), so the exposure is one request, not
  "however long the popup has been open";
- after a PUT the copy is WatchDesk's answer, never what was sent;
- writes and loads run one at a time, so two changes from this browser
  cannot interleave.

### What the API would need (to be filed as its own WatchDesk ticket)

**Request.** `PUT /api/settings` accepts a precondition and refuses a write
made on a stale read.

1. `GET /api/settings` and every `200` from `PUT` carry `ETag: "<version>"`.
   The row's `updatedAt` at full precision is enough (the body already has
   it), since a PUT that changes nothing does not move it (WD-56,
   decision 2).
2. `PUT /api/settings` reads `If-Match`. When the header is present and the
   row's version differs, nothing is written and the answer is **`412
   Precondition Failed`** with the settings as they are now in the body, in
   the shape of a `200`, and their `ETag`. The comparison and the update are
   one statement (`update … where updated_at = $1`), not a read and then a
   write.
3. With no `If-Match` the route behaves as today, so extensions already
   installed keep working. `If-Match: *` is not needed.
4. CORS for the extension: `If-Match` in `Access-Control-Allow-Headers`,
   `ETag` in `Access-Control-Expose-Headers`.
5. The web Settings page sends `If-Match` too, and copies through any field
   it does not know (today it drops them: WD-78, Known limitations), or the
   precondition protects one side only.

Optional, and it would remove most of the need: `PATCH /api/settings` taking
any subset of the fields and merging them in one transaction. A single-field
change would then need no read at all.

**What the extension would then do with a 412**, in `readModifyWrite()` and
nowhere else:

1. Take the settings from the 412's body (no second GET) and apply the same
   change to them again. A change is already "these fields" or, for the
   keyword filter, a function of the current document, so it re-applies
   without a new idea of merging.
2. PUT again with the new `ETag`. Three attempts in all.
3. After the third 412: refuse the change like any other refusal ("Your
   settings were changed somewhere else at the same moment. Try again."),
   store the copy from the last body, and put the control back. The watcher
   report records a failure and is sent again on the next sync, as now.
4. A 412 is never a reason to disconnect, to queue the change, or to show a
   merge screen.

## How it works

**The tick tells an open popup.** `syncSettingsBeforeCheck()` in
`background.js` wraps the tick's `syncAccountSettings()`: it compares what
the popup would show before and after (the four settings, the mode, the
problem, and whether a first load has happened) and, only if that differs,
sends `{ type: "settings-changed", settings, settingsSync }`. The popup's
listener hands it to `applySettingsAnswer()`, the function that already
applies the answer to `sync-settings`: it leaves the new-keyword box and its
focus alone, and does not redraw the controls while a change of the user's
is still waiting for its answer. With no account connected, and while the
import question is unanswered, it returns before doing anything.

**A keyword change is a change, not a list.** The popup still sends the
whole `{ enabled, keywords }` it wants (the shipped message, unchanged). In
connected mode the worker compares it with the copy, which is what the popup
was showing, to find what the user did: the switch turned, keywords added,
keywords removed. `saveAccountTitleFilter()` passes
`changeAccountSettings()`'s read-modify-write a function, and
`mergeTitleFilter(current, shown, wanted)` applies exactly those to the
filter just read from the account. Two spellings that differ only in letter
case are one keyword, as on WatchDesk. The account's order is kept and
additions go last. The result is checked against WatchDesk's limits before
the PUT, so a list the web has filled to 100 refuses the 101st with the
limit's words, with no write. The local copy is never the PUT body.

### Messages

| Message | Direction | When |
|---|---|---|
| `settings-changed` `{ settings, settingsSync }` (new) | worker → popup | A tick's settings fetch changed something the popup shows. Never with no account connected. Never holds the token. |

No message the popup sends has changed. No storage key is new.

## Decisions taken

The handoff said to proceed without stopping. Each of these is the option I
would have recommended and is open to challenge at review.

1. **No separate settings poll.** The check tick is the poll. A faster one
   (say every minute) would cost 1,440 requests a day per browser against 48
   at a 30-minute interval, to make four settings arrive earlier than
   anything can use them: the sound, mute and the filter act only during a
   check. Only a shortened interval would arrive sooner, and the popup
   already loads on opening. The criterion says "next poll/check cycle",
   which this is.
2. **`watcherState` stays one-way: reported, never read back.** CLAUDE.md
   and AGENTS.md state it as a rule (WD-71, WD-79), the web has no control
   that sets it (WD-78, decision 2: the value is "whichever browser reported
   last"), and one value per account cannot say which browser to pause. So
   the handoff's question "which wins when the web says paused and the
   extension was just started locally" has one answer here: this browser,
   always. A pause from the web needs a per-device state and a web control:
   a ticket of its own (WD-71's follow-up says the same).
3. **The popup is told only when something it shows changed**, not on every
   tick: the line is a live region, and an unchanged tick has nothing to
   say.
4. **The keyword change is worked out in the worker, against the copy**,
   rather than by a new message from the popup. The popup's messages are
   pinned by the parity tests and are identical with no account connected;
   this way they did not change at all.
5. **Paused means no settings fetch either.** WD-71 chose not to wake a
   paused extension to talk to WatchDesk; a paused browser acts on no
   setting. The change arrives with the first check after Start, before
   that check, or when the popup opens.
6. **A web interval takes effect a whole new interval after the tick that
   fetched it** (WD-79's rule, kept): that tick is itself a check.
7. **No guard for a select that has the focus.** A select keeps the focus
   after it was used, so skipping a focused one would leave it stale for as
   long as the popup stayed open. Text being typed (the only free-text
   field) and a change in flight are protected, as before.
8. **The conflict window is documented, not disguised** (section above).
9. **`tests/background-wiring.test.js`, WD-59 block:** its collector of
   "what the popup received" now leaves out `settings-changed`. Those tests
   connect and tick in one step, so the connection's first settings load now
   tells the popup; that message is this ticket's subject and is asserted in
   `settings-two-way`.

## Known limitations

- **A web save between this browser's GET and PUT is lost.** One request
  long. Needs the server (above).
- **Shortening the interval on the web takes up to the old interval** to
  take effect: 30 minutes at worst.
- **While paused, a web change is not fetched** until the popup opens or
  watching starts (decision 5).
- **The keyword comparison is against the copy.** If the copy changed after
  the popup last drew its chips (a tick landed while a change of the user's
  was in flight), the next keyword change is worked out against a list the
  user was not looking at; the result is then the popup's list, as before
  this ticket, never worse.
- **A keyword removed on the web and still on show in the popup** cannot be
  added back from that popup until it has redrawn: the popup thinks it is
  already there and sends nothing. The next tick or reopening fixes it.
- **A select open at the moment a tick lands** has its value changed under
  it; whatever the user then picks is saved (decision 7).
- **Two browsers on one account** each follow the account's settings at
  their own next tick. `watcherState` on the account is whichever reported
  last (WD-71).
- WD-79's limitations stand: `chrome.storage.sync` shared between Chrome
  profiles, no "defaults" button for the account's settings.

## Manual verification (Chrome)

1. Load the repository root unpacked, pointed at a local WatchDesk
   (`WATCHDESK_ENV = "development"`; do not commit that), and connect an
   account. Set "Check every" to 1 min.
2. Close the popup. On WatchDesk's Settings page choose another sound and
   save. Within a minute a new posting is announced with that sound.
3. Open the popup and leave it open. On the web, change the interval and
   mute and save. Within a minute both controls change without touching the
   popup.
4. In the popup add a keyword. Reload the web's Settings page: it is there.
5. With the popup open, add a keyword on the web and save; in the popup,
   before the next check, turn the filter off. Reload the web page: the
   filter is off and the web's keyword is still there.
6. Pause Watching, change the sound on the web, wait: nothing is fetched.
   Start Watching: the first check uses the new sound.
